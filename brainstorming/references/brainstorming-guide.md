# Brainstorming Guide

本文件补充 `SKILL.md` 主流程。退出条件和写盘关卡以 `SKILL.md` 为准。

## Context exploration priorities

1. README、CLAUDE.md、AGENTS.md 或等效项目文档。
2. package.json、pyproject.toml、Cargo.toml、go.mod、pom.xml 等项目配置。
3. 与本次变更相关的入口点、路由、服务和数据访问层。
4. 需要理解近期变化时，查看最近 10 个提交。
5. 需求依赖真实 schema 时，使用只读数据库工具核实。

STOP when 你能说明项目目的、技术栈、目录结构和本次变更所在边界。

## Decomposition heuristics

以下信号表明需求可能需要拆分：

- 跨越多个独立领域或能力。
- 各部分需要不同的数据模型或外部集成。
- 各部分可以由不同团队拥有或独立交付。
- 某一部分的方案选择会阻断其他部分。

拆分时列出子项目、依赖关系和推荐顺序，并等待用户确认。

多个模块上围绕同一目标的小改动不自动构成大需求。

## Question patterns

提问只覆盖无法从项目中检索、只能由用户决定的信息：

- Purpose：谁使用它，它帮助做出什么决定？
- Priority：必须交付什么，什么可以放弃？
- Constraints：时延、规模、安全、合规、成本和运营限制是什么？
- Success：怎样判断需求已经成功？
- Data：输入、输出和事实源分别是什么？
- Risk：哪些失败模式必须在当前范围内处理？

每轮只问一个原子问题。多选题能表达真实取舍时，优先给选项和你的建议。

## Design depth guidance

- 中等变更：写清主路径、关键数据或契约变化，以及主要错误场景。
- 复杂变更：增加关键失败路径、状态转换、迁移和可靠性机制。
- 没有某类变化时，不为满足模板强行添加空的数据、接口或状态章节。

设计深度由实现风险决定，不由用户提示词的长度决定。

## Existing codebase tactics

- 识别可复用的接缝并遵守本地模式。
- 先验证需求是否与现有能力重复或冲突。
- 设计声明能通过代码、配置、数据库或历史核实时，主动核实。
- 只有重构能解除当前目标的阻塞时才纳入范围。
- 优先减少耦合，并避免改变无关行为。

## Post-design complexity examples

**通常为简单：**

- 局部校验规则。
- 单个 UI 状态调整。
- 遵循既有模式、测试和回滚都直接的小型命令行为变更。

**通常为中等或复杂：**

- 数据库结构或数据迁移。
- 新外部服务或消息集成。
- 认证、权限或公共 API 契约变化。
- 跨组件工作流。
- 并发、一致性、可靠性或运营上线风险。
- 仍有未解决的设计问题。

错误设计难以回滚或影响多个调用方时，应推荐 `design-review`。

## Fuzziness diagnosis

| Level | Signal | Strategy |
|-------|--------|----------|
| Problem unclear | 描述症状而非目标 | 重新界定问题 |
| Direction unclear | 目标存在但方向未知 | 探索代表性方向 |
| Boundaries unclear | 功能明确但边界未知 | 排查领域盲点 |
| Solution unclear | 需求和范围已知 | 确认约束后比较方案 |

技术术语丰富不代表 Solution 或意图已经明确。

## Assumption challenging

对非简单需求识别 1-3 个可能影响方向的假设，并表述为值得确认的事项：

- 用户会按设想方式使用功能。
- 现有架构无需改变即可支持需求。
- 所有能力必须在一次发布中完成。
- 性能或规模不会成为问题。
- 现有数据模型已经足够。

一次只选择最可能改变方案的上游假设提问。

## Blind spot scanning

按领域选择最相关的检查项，不机械遍历全部清单。

### User-facing features

- 空、加载和错误状态。
- 权限与访问控制。
- 撤销或回滚。
- 离线行为。
- 无障碍和国际化。
- 移动端或响应式行为。

### Data changes

- 历史数据迁移和回填。
- 一致性、并发与幂等。
- 保留和清理策略。
- 隐私、合规、备份和恢复。

### Integrations

- 速率限制和配额。
- 认证与凭证轮换。
- 超时、重试、重放和去重。
- 失败回退或降级。
- 版本和向后兼容。
- 监控和告警。

## Divergent exploration techniques

按需使用，不为每个需求完整执行：

- 解除约束：先描述理想状态，再逐个加回现实约束。
- 反向分析：识别会让功能失败的条件，并判断是否需要处理。
- 切换视角：从用户、管理员、运维和调用方角度检查。
- 时间跨度：识别半年后难以逆转的选择。
- 强制优先级：要求用户在有限交付项中选择最重要内容。
- 类比借鉴：检查领域内已有成熟模式。

## When to stop brainstorming

退出条件以 `SKILL.md` STEP 4 为唯一权威。以下仅是辅助信号：

- 能说明用户想要什么、为什么需要，以及明确不要什么。
- 关键约束和成功标准已知。
- 适用假设和盲点已经确认或排除。
- 项目事实与用户偏好可以清楚区分。

不要使用“保持稳定若干轮”这类无法可靠执行的数值阈值。
