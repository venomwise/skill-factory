## D1：支付回调幂等性设计

### 问题来源
**Review 报告 P0-阻断 #1：** "PRD 未说明如何保证回调幂等性。支付网关可能重复推送回调,如果不做幂等处理,会导致：订单状态被重复更新、重复发放商品/服务、资金账户异常"

**PRD 相关章节：** 2.2 支付结果处理、3.1 支付流程第 5-6 步

### 为什么需要决策？
这不是简单的文字补充，而是核心架构设计决策：
1. 直接影响数据一致性和资金安全（金融项目的核心要求）
2. 需要在性能、复杂度、可靠性之间权衡
3. 涉及数据库设计、缓存策略、分布式锁等技术选型

### 项目现状
- **当前 PRD 状态：** 只提到"接收支付网关回调、更新订单状态"，未提及幂等性
- **支付网关特性：** 微信支付和支付宝都会在回调失败时进行重试（通常 8 次，间隔递增）
- **风险评估：** 无幂等性保护的情况下，1% 的重复回调概率在日均 10 万笔交易中意味着 1000 笔异常
- **合规要求：** 金融系统必须保证"有且仅有一次"的状态变更

### 方案分析

#### 方案 A：数据库唯一索引 + 状态机

**实现方式：**
- 在订单支付记录表增加唯一索引 `unique(order_id, trade_no)`
- 使用数据库事务 + 状态机控制订单状态流转
- 重复回调时数据库报唯一索引冲突，直接返回成功

**优点：**
- 实现简单，开发成本约 2 人日
- 利用数据库特性天然保证幂等性
- 无需引入额外组件（Redis、分布式锁等）
- 可靠性高，数据库事务保证原子性

**缺点：**
- 数据库压力较大，每次回调都需要写库
- 高并发时可能有死锁风险（需要合理设计索引和事务范围）
- 唯一索引冲突会产生异常日志（虽然是预期行为，但会干扰监控）

**风险：**
- 如果订单表和支付记录表分库，需要考虑分布式事务
- 极端情况下数据库不可用时，回调处理会完全失败

**适用场景：** 中小规模系统（日均 < 50 万笔），单库部署

**开发成本：** 2 人日  
**技术债务：** 低（标准做法）

---

#### 方案 B：分布式锁 + 防重表

**实现方式：**
- 使用 Redis 分布式锁，锁键为 `payment:lock:{order_id}`
- 维护独立的防重表记录已处理的 `(order_id, trade_no)`
- 获取锁后先查防重表，存在则直接返回成功
- 处理成功后写入防重表，释放锁

**优点：**
- 性能好，Redis 操作快（QPS 可达 10 万+）
- 锁粒度细（订单级别），并发能力强
- 防重表可以设置 TTL 自动清理（如保留 30 天）
- 业务逻辑清晰，易于扩展（如记录每次回调时间、来源等）

**缺点：**
- 复杂度较高，开发成本约 4 人日
- 依赖 Redis，增加系统依赖和运维成本
- 需要处理 Redis 故障场景（降级为数据库锁）
- 锁超时时间难以设定（太短可能误释放，太长影响并发）

**风险：**
- Redis 主从切换时可能丢锁（需要使用 Redlock 或主从 + 哨兵）
- 分布式锁的正确性依赖时钟同步
- 防重表和业务表数据不一致的补偿逻辑复杂

**适用场景：** 大规模系统（日均 > 50 万笔），已有 Redis 基础设施

**开发成本：** 4 人日  
**技术债务：** 中（需要维护分布式锁和降级逻辑）

---

#### 方案 C：消息队列 + 消费幂等

**实现方式：**
- 回调请求先写入消息队列（Kafka/RabbitMQ）
- 消费者从队列获取消息，使用消息 ID 做幂等
- 利用消息队列的重试机制保证最终一致性

**优点：**
- 解耦，回调接口快速响应（只负责写队列）
- 天然支持削峰填谷，高并发下更稳定
- 消息队列自带重试、死信队列等机制
- 便于后续扩展（如异步通知用户、记录审计日志等）

**缺点：**
- 架构复杂度最高，开发成本约 6 人日
- 引入消息队列组件，运维成本增加
- 异步处理，用户感知延迟（通常增加 100-500ms）
- 需要额外处理消息积压、消费失败等问题

**风险：**
- 消息队列故障会导致订单状态延迟更新
- 消息顺序性问题（如先收到退款回调，后收到支付回调）
- 需要设计合理的监控和告警体系

**适用场景：** 超大规模系统（日均 > 100 万笔），或已有消息队列基础设施

**开发成本：** 6 人日  
**技术债务：** 高（需要维护消息队列和复杂的异步逻辑）

### 推荐方案

**推荐方案 A：数据库唯一索引 + 状态机**

### 推荐理由

1. **成本效益比最优**
   - 开发成本最低（2 人日 vs 4-6 人日）
   - 无需引入新组件，运维成本为零
   - 对于金融项目的"稳妥第一"原则最契合

2. **可靠性最高**
   - 数据库事务的 ACID 特性是久经考验的
   - 无分布式系统的复杂性（无网络分区、时钟漂移等问题）
   - 故障场景少，易于测试和验证

3. **符合项目现状**
   - PRD 提到"支付成功率 > 99%"，未提及极高并发要求
   - 新项目初期流量不大，过早优化是技术债务
   - 金融项目更看重"绝对正确"而非"极致性能"

4. **扩展性充足**
   - 日均 50 万笔以内完全够用（单表千万级数据无压力）
   - 未来流量增长时可以平滑升级到方案 B（改动成本可控）
   - 数据库分库分表方案已经非常成熟

5. **对标行业实践**
   - 支付宝、微信支付的商户侧 SDK 示例代码都采用此方案
   - 国内主流支付公司（如 Ping++、BeeCloud）的官方文档推荐此方案

### 具体实现要点

**数据库设计：**
```sql
-- 订单表
CREATE TABLE `order` (
  `id` BIGINT PRIMARY KEY AUTO_INCREMENT,
  `order_id` VARCHAR(64) NOT NULL UNIQUE COMMENT '业务订单号',
  `status` TINYINT NOT NULL DEFAULT 0 COMMENT '0-待支付 1-已支付 2-已关闭 3-已退款',
  `amount` DECIMAL(10,2) NOT NULL COMMENT '订单金额',
  `created_at` DATETIME NOT NULL,
  `updated_at` DATETIME NOT NULL,
  INDEX `idx_status_created` (`status`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';

-- 支付记录表（防重核心）
CREATE TABLE `payment_record` (
  `id` BIGINT PRIMARY KEY AUTO_INCREMENT,
  `order_id` VARCHAR(64) NOT NULL COMMENT '业务订单号',
  `trade_no` VARCHAR(128) NOT NULL COMMENT '支付平台交易号',
  `pay_channel` VARCHAR(32) NOT NULL COMMENT '支付渠道：wechat/alipay',
  `amount` DECIMAL(10,2) NOT NULL COMMENT '实付金额',
  `status` TINYINT NOT NULL COMMENT '1-成功 2-失败',
  `callback_time` DATETIME NOT NULL COMMENT '回调时间',
  `created_at` DATETIME NOT NULL,
  UNIQUE KEY `uk_order_trade` (`order_id`, `trade_no`) COMMENT '幂等性保证',
  INDEX `idx_trade_no` (`trade_no`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='支付记录表';
```

**状态机设计：**
- 订单状态只能单向流转：待支付 → 已支付 → 已关闭/已退款
- 在更新语句中增加状态前置条件：`UPDATE order SET status=1 WHERE order_id=? AND status=0`
- 影响行数为 0 时说明已处理过，直接返回成功

**事务边界：**
```java
@Transactional(rollbackFor = Exception.class)
public void handlePaymentCallback(PaymentCallbackDTO dto) {
    try {
        // 1. 插入支付记录（唯一索引保证幂等）
        paymentRecordMapper.insert(record);
        
        // 2. 更新订单状态（状态机保证幂等）
        int affected = orderMapper.updateStatus(orderId, 0, 1);
        if (affected == 0) {
            log.warn("订单状态已变更，可能重复回调: {}", orderId);
        }
        
        // 3. 发放商品/服务
        deliverService.deliver(orderId);
        
    } catch (DuplicateKeyException e) {
        // 重复回调，唯一索引冲突，正常情况
        log.info("重复回调，幂等性生效: {}", dto.getTradeNo());
        return; // 返回成功给支付网关
    }
}
```
