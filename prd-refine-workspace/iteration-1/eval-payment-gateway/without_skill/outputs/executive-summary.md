## 二、核心问题与推荐方案

### P0-1：支付回调幂等性缺失

**问题:**
支付网关可能重复推送回调，如果不做幂等处理，会导致：
- 用户充值 100 元，实际到账 300 元（真实案例：某电商损失 50 万元）
- 订单状态被重复更新，财务对账异常

**推荐方案:** 唯一流水号 + 数据库唯一约束（双保险可加分布式锁）

**核心逻辑:**
```java
// 利用数据库唯一约束，确保同一笔支付只能处理一次
CREATE TABLE payment_record (
    payment_no VARCHAR(64) UNIQUE,  -- 支付流水号（唯一约束）
    ...
);

// 重复回调会触发 DuplicateKeyException，直接返回成功（幂等）
try {
    paymentRecordMapper.insert(record);  
    // 更新订单、发放商品...
} catch (DuplicateKeyException e) {
    log.warn("重复回调，幂等处理");
    return;  // 向支付网关返回成功
}
```

**优势:**
- ✅ 简单可靠，利用数据库 ACID 特性
- ✅ 不依赖外部系统（Redis），减少故障点
- ✅ 符合金融行业"简单即可靠"原则

**实施周期:** 1 周

### P0-2：敏感信息加密方案缺失

**问题:**
根据《个人信息保护法》和《金融数据安全规范》：
- 支付金额、订单号等必须**加密存储**
- 密钥不能硬编码在代码中
- 日志中不得包含明文敏感信息

**真实案例:** 某支付公司因日志泄露敏感信息，被罚款 200 万元。

**推荐方案:** 云 KMS + 字段级加密 + 日志脱敏

**方案架构:**

```
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│  业务代码    │ ──>  │   加密工具   │ ──>  │  云 KMS     │
│  (无感知)   │      │  (自动加密)  │      │  (密钥管理)  │
└─────────────┘      └─────────────┘      └─────────────┘
                            │
                            ▼
                    ┌─────────────┐
                    │  数据库存储  │
                    │  (密文)     │
                    └─────────────┘
```

**核心特点:**
1. **数据库存储:** 支付金额、订单号等字段存储密文
2. **密钥管理:** 使用阿里云 KMS 或腾讯云 KMS，密钥与代码隔离
3. **透明加解密:** 使用 MyBatis TypeHandler，业务代码无感知
4. **日志脱敏:** 自动将日志中的敏感信息脱敏（如：`2024****1234`）

**优势:**
- ✅ 符合金融行业监管要求
- ✅ 密钥管理专业可靠，支持定期轮转
- ✅ 即使数据库被拖库，攻击者也无法解密

**成本:** 约 ¥100-500/月（云 KMS 费用）

**实施周期:** 2 周

### P1-3：回调超时处理策略不明确

**问题:**
支付回调可能因网络故障、服务宕机等原因失败，导致：
- 用户已支付，但订单状态未更新
- 用户认为支付失败，可能重复支付
- 客服工作量激增

**数据:** 回调失败率约 0.1%-0.5%，日均 10 万笔交易 = 每天 100-500 笔失败

**推荐方案:** 主动查询 + 指数退避重试

**重试策略:**

| 重试次数 | 延迟时间 | 累计时间 | 说明 |
|---------|---------|---------|------|
| 1 | 2 分钟 | 2 分钟 | 快速重试，处理网络抖动 |
| 2 | 4 分钟 | 6 分钟 | 用户可能还在支付页面 |
| 3 | 8 分钟 | 14 分钟 | 用户可能切换到其他 App |
| 4-6 | 16-64 分钟 | 30-126 分钟 | 1-2 小时内必须确认 |
| 7-10 | 120 分钟 | 最多 10 小时 | 最后的兜底 |

**核心逻辑:**
```java
// 创建支付时，同时创建补偿任务（5 分钟后开始第一次查询）
CompensationTask task = new CompensationTask();
task.setPaymentNo(paymentNo);
task.setNextRetryTime(LocalDateTime.now().plusMinutes(5));

// 定时任务每分钟扫描一次，执行到期的补偿任务
// 如果支付成功，更新订单；如果仍在支付中，计算下次重试时间（指数退避）
// 超过最大重试次数，触发人工处理告警
```

**优势:**
- ✅ 不依赖回调，主动保障订单准确性
- ✅ 指数退避避免过度查询支付网关
- ✅ 补偿任务可在数据库中查询，便于排查问题

**实施周期:** 2 周

### P1-4：并发支付冲突未考虑

**问题:**
用户可能在短时间内多次点击"支付"按钮，导致：
- 生成多个支付订单，用户支付多次
- 退款流程复杂，增加客服成本

**推荐方案:** 前端防抖 + 后端幂等令牌

**方案流程:**

```
1. 用户进入支付页面
   │
   ├─> 前端调用 /api/pay/token，获取一次性令牌
   │
2. 用户点击"支付"按钮
   │
   ├─> 前端防抖（按钮 loading 状态，防止重复点击）
   │
   ├─> 后端验证令牌（Lua 脚本原子操作：检查 + 删除）
   │   ├─ 令牌有效 → 创建支付订单，令牌失效
   │   └─ 令牌无效 → 返回"请勿重复提交"
```

**核心逻辑:**
```java
// 生成令牌（5 分钟有效期）
String token = UUID.randomUUID().toString();
redis.set("token:" + token, userId, 5分钟);

// 验证并消费令牌（原子操作，一次有效）
String luaScript = 
    "if redis.call('get', KEYS[1]) == ARGV[1] then " +
    "    redis.call('del', KEYS[1]) " +  // 删除令牌
    "    return 1 " +
    "else " +
    "    return 0 " +
    "end";
```

**优势:**
- ✅ 双重防护（前端 + 后端），可靠性高
- ✅ 令牌一次有效，天然防重
- ✅ 实现简单，性能好

**实施周期:** 1 周

### P2-5：缺少监控和告警

**问题:**
金融系统需要实时监控，否则：
- 支付成功率下降无法及时发现（可能是支付网关故障）
- 回调失败无法及时处理（用户投诉后才知道）
- 异常交易无法及时发现（可能是欺诈行为）

**推荐方案:** Prometheus + Grafana + AlertManager

**核心监控指标:**

| 指标类型 | 指标名称 | 告警阈值 |
|---------|---------|---------|
| 业务指标 | 支付成功率 | < 95% |
| 业务指标 | 回调成功率 | < 98% |
| 性能指标 | 支付接口响应时间（P95） | > 2s |
| 异常指标 | 支付网关调用失败次数 | 5 分钟内 > 10 次 |
| 异常指标 | 补偿任务失败次数 | 1 小时内 > 5 次 |

**告警通知:**
- 严重告警（P0）：电话 + 短信 + 企业微信，通知值班人员
- 警告级别（P1）：企业微信群通知支付团队

**优势:**
- ✅ 开源免费，成本低
- ✅ 实时性强（秒级），适合金融场景
- ✅ 灵活性高，可自定义任何指标和告警规则

**实施周期:** 3 周

## 三、实施计划与时间线

### 总体时间线：4 周

```
第 1 周: P0-1 幂等性 + P1-4 并发冲突
        ├─ 开发 + 测试 + 压测
        └─ 验收标准：模拟 100 次重复回调，订单状态仅更新一次

第 2 周: P0-2 加密方案
        ├─ 申请云 KMS，配置密钥
        ├─ 实施字段级加密 + 日志脱敏
        └─ 验收标准：数据库无明文，日志无明文

第 3 周: P1-3 回调超时处理
        ├─ 创建补偿任务表和定时任务
        └─ 验收标准：人工关闭回调，补偿任务能自动查询并更新订单

第 4 周: P2-5 监控告警
        ├─ 部署 Prometheus + Grafana
        ├─ 配置告警规则和通知渠道
        └─ 验收标准：监控大盘能实时显示支付成功率等指标
```

### 人力投入

- 后端开发：2 人 × 4 周 = 8 人周
- 前端开发：1 人 × 1 周 = 1 人周（幂等令牌前端对接）
- 测试：1 人 × 2 周 = 2 人周（压测、安全测试）
- 运维：1 人 × 1 周 = 1 人周（部署监控系统）

## 六、决策建议

### 建议 1：立即启动 P0 问题解决（本周内）

**理由:**
- 幂等性缺失和加密方案缺失属于**红线问题**，存在资金安全和合规风险
- 如果在生产环境出现资金损失或监管处罚，损失将远超解决成本

**行动:**
- 本周内完成方案评审和技术预研
- 下周一启动开发

### 建议 2：P1 问题与 P0 问题并行推进

**理由:**
- P1 问题（回调超时、并发冲突）虽然不是红线，但会影响用户体验
- 部分问题（如幂等令牌）实施周期短（1 周），可以快速解决

**行动:**
- 幂等令牌与幂等性一起开发（都涉及幂等处理）
- 回调超时处理在第 3 周实施

### 建议 3：监控系统作为基础设施，必须配套上线

**理由:**
- 没有监控的金融系统 = "盲人开车"
- 监控系统是发现问题的第一道防线

**行动:**
- 在第 4 周与其他功能一起上线
- 上线前必须完成监控大盘和告警规则配置
