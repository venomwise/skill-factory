## D1: 权限模型设计(角色定义、权限边界、编辑规则)

### 问题来源
- **Review P1-1:** "权限模型设计不明确" - 未明确角色、权限、粒度
- **Review P1-3:** "用户编辑权限边界不清" - 管理员编辑范围不明确
- **PRD 引用:** 第 2.3 节"用户编辑"和第 3.1 节"用户表"

### 项目现状
根据 PRD 和项目背景:
- **用户群体:** 内部员工管理系统
- **当前描述:** 只提到"管理员可以编辑用户信息、分配权限"
- **数据模型:** 用户表有 `role` 字段,但未定义可选值
- **交付时间:** 下个月中旬上线(约 45 天),需要快速明确需求

### 方案分析

#### 方案 A: 简单两级权限模型(管理员 + 普通员工)

**角色定义:**
- **管理员(admin):** 完全权限,可管理所有用户
- **普通员工(employee):** 只读权限,只能查看自己的信息

**权限矩阵:**
| 功能 | 管理员 | 普通员工 |
|------|--------|----------|
| 查看用户列表 | ✓ | ✗ |
| 查看自己信息 | ✓ | ✓ |
| 查看他人信息 | ✓ | ✗ |
| 编辑自己信息 | ✓ | ✗ |
| 编辑他人信息 | ✓ | ✗ |
| 分配权限 | ✓ | ✗ |

**编辑规则:**
- 管理员可以编辑所有用户(包括自己和其他管理员)
- 管理员可以修改任何用户的角色

**优点:**
- 实现简单,开发工作量约 3-5 人日
- 权限逻辑清晰,容易测试和维护
- 适合小团队(员工数 < 100)的内部系统

**缺点:**
- 缺少审计机制(管理员互相修改无制约)
- 普通员工不能自助修改基本信息(如联系方式)
- 扩展性有限,未来如果需要部门经理等中间角色需要重构

**风险:**
- 如果管理员账号泄露,可能导致所有数据被篡改
- 多个管理员同时操作可能冲突

#### 方案 B: 三级权限模型(超级管理员 + 管理员 + 普通员工)

**角色定义:**
- **超级管理员(super_admin):** 最高权限,通常只有 1-2 人
- **管理员(admin):** 日常管理权限,可管理普通员工
- **普通员工(employee):** 只读权限,可编辑自己的基本信息

**权限矩阵:**
| 功能 | 超级管理员 | 管理员 | 普通员工 |
|------|------------|--------|----------|
| 查看用户列表 | ✓ | ✓ | ✗ |
| 查看自己信息 | ✓ | ✓ | ✓ |
| 查看他人信息 | ✓ | ✓(仅员工) | ✗ |
| 编辑自己基本信息 | ✓ | ✓ | ✓(有限字段) |
| 编辑他人信息 | ✓ | ✓(仅员工) | ✗ |
| 分配权限(管理员) | ✓ | ✗ | ✗ |
| 分配权限(员工) | ✓ | ✓ | ✗ |

**编辑规则:**
- 超级管理员可以编辑所有用户
- 管理员只能编辑普通员工,不能编辑管理员
- 普通员工可以编辑自己的姓名、联系方式,不能修改角色和状态

**优点:**
- 权限分层更合理,降低误操作风险
- 普通员工可以自助更新信息,减少管理员工作量
- 超级管理员作为安全阀,防止管理员滥用权限

**缺点:**
- 实现复杂度增加,开发工作量约 6-8 人日
- 权限判断逻辑更复杂,需要更多测试用例
- 需要明确超级管理员的分配和交接流程

**风险:**
- 如果超级管理员账号丢失或离职,可能导致管理权限无法变更

#### 方案 C: 动态 RBAC 权限管理

**角色定义:**
- 角色可动态配置(通过管理界面创建、删除、修改角色)
- 权限细粒度到具体操作(查看、新增、编辑、删除)
- 支持权限继承和组合

**优点:**
- 扩展性极强,未来需求变化无需改代码
- 适合大型组织(员工数 > 500)
- 可以灵活配置部门经理、区域经理等角色

**缺点:**
- 开发成本高,需要 15-20 人日
- 需要额外开发权限管理界面
- 对于简单场景来说过度设计
- 配置错误可能导致安全漏洞

**风险:**
- 当前项目时间紧(45 天上线),可能无法按时交付
- PRD 中未提及动态权限配置需求

### 影响分析

| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| **用户体验** | 员工需联系管理员修改信息 | 员工可自助更新基本信息 | 灵活但学习成本高 |
| **开发成本** | 3-5 人日 | 6-8 人日 | 15-20 人日 |
| **可维护性** | 简单,容易理解 | 中等,需要理解层级关系 | 复杂,需要专门文档 |
| **扩展性** | 差,新增角色需改表结构 | 中等,可小幅调整 | 好,完全灵活 |
| **安全性** | 一般,管理员权限过大 | 较好,有权限分层 | 好,但配置错误有风险 |
| **交付风险** | 低 | 低 | 高(可能延期) |

### 推荐方案: 方案 B(三级权限模型)

**推荐理由:**

1. **平衡性好:** 既满足当前需求,又为未来预留一定扩展空间
2. **开发可控:** 6-8 人日在 45 天时间线内完全可行
3. **安全性提升:** 避免了方案 A 中管理员权限过大的问题
4. **用户体验:** 普通员工可以自助更新基本信息,符合现代产品设计理念
5. **符合内部系统特点:** 内部员工管理系统通常有明确的管理层级

**实施建议:**
- 在 PRD 中补充完整的权限矩阵表格
- 明确可编辑字段的范围(员工可改:姓名、手机;不可改:邮箱、角色、状态)
- 在"未来演进"章节说明:如果组织规模扩大(>500 人)或需要更复杂的部门权限,可在 V2 升级为 RBAC 模型
