# 针对当前项目的最终建议

## 项目现状分析

**技术栈**: Spring Boot 2.7.0 + MySQL + JPA  
**缺少组件**: Redis、消息队列  
**性能目标**: 1000 QPS  
**核心问题**: 并发超卖、超时释放、性能瓶颈

---

## 推荐方案：分阶段演进策略

### 阶段一：立即实施（本周完成）

**方案**: MySQL 悲观锁 + 定时任务

#### 实施内容

1. **并发控制**：使用 `SELECT ... FOR UPDATE` 行锁
2. **超时处理**：Spring `@Scheduled` 定时任务（每 5 分钟扫描）
3. **数据库优化**：添加索引、调优连接池

#### 工作量评估

- 开发工作量：2-3 人日
- 测试工作量：1 人日
- 无需新增基础设施

#### 性能预期

- **支持 QPS**: 300-500
- **响应时间**: 50-100ms
- **数据一致性**: 强一致

#### 风险评估

⚠️ **风险**: 如果实际流量超过 500 QPS，会出现性能瓶颈  
✅ **应对**: 提前准备阶段二方案，流量监控达到 80% 时启动升级

---

### 阶段二：性能不足时实施（预留 2 周）

**方案**: Redis 分布式锁 + MySQL + 延迟消息队列

#### 实施内容

1. **分布式锁**：Redisson 分布式锁保证并发安全
2. **超时处理**：RabbitMQ 延迟消息（精确到秒）
3. **降级方案**：Redis 故障时降级到方案一

#### 新增组件

```yaml
Redis: 单机或哨兵模式（3 台）
RabbitMQ: 单机或集群（3 台）
```

#### 工作量评估

- 基础设施部署：3 人日
- 代码改造：5 人日
- 压测和调优：2 人日
- **总计**: 10 人日（约 2 周）

#### 性能预期

- **支持 QPS**: 800-1200
- **响应时间**: 20-50ms
- **数据一致性**: 强一致

#### 成本评估

- Redis 服务器：3 台（每台 8GB 内存）
- RabbitMQ 服务器：3 台（每台 8GB 内存）
- **总成本**: 约 6 台服务器的运维成本

---

### 阶段三：秒杀场景时实施（按需）

**方案**: Redis 缓存 + 异步持久化 + Canal

#### 实施内容

1. **库存缓存**：Redis Lua 脚本原子扣减
2. **异步持久化**：消息队列批量写入 MySQL
3. **数据一致性**：Canal 监听 Binlog 对账
4. **限流降级**：Sentinel 流量控制

#### 新增组件

```yaml
Canal: MySQL Binlog 监听
Sentinel: 流量控制和降级
```

#### 工作量评估

- Canal 部署和集成：3 人日
- Redis 缓存层开发：5 人日
- 异步持久化逻辑：3 人日
- 数据对账机制：3 人日
- 压测和调优：3 人日
- **总计**: 17 人日（约 3-4 周）

#### 性能预期

- **支持 QPS**: 10000+
- **响应时间**: < 10ms
- **数据一致性**: 最终一致（秒级对账）

## 关键决策点

### 决策 1: 是否立即引入 Redis？

**建议**: ❌ **不建议**

**理由**:
1. 当前没有 Redis 运维经验，引入会增加风险
2. 如果实际流量 < 500 QPS，方案一足够
3. 先用方案一验证业务逻辑，再优化性能

**决策依据**: 先跑通业务，再优化性能

---

### 决策 2: 超时订单如何处理？

**建议**: ✅ **定时任务（阶段一）** → 延迟消息（阶段二）

**理由**:
1. 定时任务实现简单，无需额外组件
2. 5 分钟扫描频率对业务影响小
3. 阶段二引入消息队列后升级为延迟消息

**定时任务配置**:
```java
@Scheduled(cron = "0 */5 * * * ?")  // 每 5 分钟执行
```

---

### 决策 3: 如何保证数据一致性？

**建议**: ✅ **数据库事务 + 悲观锁**

**理由**:
1. MySQL 事务保证 ACID
2. 行锁保证并发安全
3. 强一致性，无需对账

**事务配置**:
```java
@Transactional(rollbackFor = Exception.class)
```

## 风险管理

### 风险 1: 定时任务故障导致库存永久锁死

**概率**: 中  
**影响**: 高

**应对措施**:
1. 定时任务执行日志监控
2. 设置告警：超过 10 分钟未执行则报警
3. 提供手动触发接口
4. 准备数据修复脚本

```sql
-- 紧急修复脚本：释放所有超时预占库存
UPDATE product_stock ps
SET ps.stock = ps.stock + ps.reserved_stock,
    ps.reserved_stock = 0
WHERE ps.product_id IN (
    SELECT o.product_id FROM `order` o
    WHERE o.status = 'PENDING'
    AND o.created_at < DATE_SUB(NOW(), INTERVAL 30 MINUTE)
);
```

---

### 风险 2: 数据库连接池耗尽

**概率**: 中  
**影响**: 高

**应对措施**:
1. 监控连接池使用率
2. 设置告警：使用率 > 80% 时报警
3. 优化慢查询
4. 调大连接池大小（最大 50）

```properties
spring.datasource.hikari.maximum-pool-size=50
```

---

### 风险 3: 热门商品成为性能瓶颈

**概率**: 高（秒杀场景）  
**影响**: 高

**应对措施**:
1. 提前识别热门商品
2. 热门商品单独处理（限流、排队）
3. 准备阶段二方案（Redis 分布式锁）
4. 紧急情况下启用降级

## 监控指标

### 核心指标

| 指标 | 目标值 | 告警阈值 |
|------|--------|---------|
| 库存扣减成功率 | > 95% | < 90% |
| 接口响应时间 P99 | < 200ms | > 500ms |
| 数据库 QPS | < 500 | > 400 |
| 连接池使用率 | < 70% | > 80% |
| 定时任务执行频率 | 5 分钟 | > 10 分钟 |

### 监控大盘

```sql
-- 库存扣减成功率
SELECT 
    COUNT(*) as total,
    SUM(CASE WHEN result = 'SUCCESS' THEN 1 ELSE 0 END) as success,
    SUM(CASE WHEN result = 'SUCCESS' THEN 1 ELSE 0 END) * 100.0 / COUNT(*) as success_rate
FROM stock_log
WHERE created_at > DATE_SUB(NOW(), INTERVAL 5 MINUTE);

-- 超时订单数量
SELECT COUNT(*) as timeout_orders
FROM `order`
WHERE status = 'PENDING'
AND created_at < DATE_SUB(NOW(), INTERVAL 30 MINUTE);
```
