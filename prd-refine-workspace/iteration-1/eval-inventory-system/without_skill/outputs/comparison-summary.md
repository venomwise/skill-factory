## 优缺点详细对比

### 方案一：MySQL 悲观锁

#### 优点

✅ **实现最简单** - 只需一条 SQL: `SELECT ... FOR UPDATE`  
✅ **强一致性** - 数据库事务 ACID 保证  
✅ **无额外依赖** - 不需要 Redis、消息队列  
✅ **运维成本低** - 只需维护数据库  
✅ **故障率低** - 组件少，出问题概率小  
✅ **易于调试** - 问题排查简单  

#### 缺点

❌ **性能瓶颈** - 500 QPS 就到极限  
❌ **锁等待长** - 并发高时大量请求排队  
❌ **热点问题** - 热门商品成为瓶颈  
❌ **扩展性差** - 加机器无法提升性能  
❌ **用户体验** - 等待时间长  

#### 适用场景

✅ 日订单量 < 10 万  
✅ 非秒杀场景  
✅ 预算有限  
✅ 团队技术栈简单  

---

### 方案二：MySQL 乐观锁

#### 优点

✅ **无锁等待** - 不阻塞其他请求  
✅ **吞吐量高** - 比悲观锁好 50%  
✅ **实现简单** - JPA `@Version` 内置支持  
✅ **适合读多写少** - 冲突少时效率高  

#### 缺点

❌ **重试频繁** - 高并发时大量失败  
❌ **用户体验差** - 失败提示"请重试"  
❌ **不适合秒杀** - 热门商品冲突率 > 50%  
❌ **浪费资源** - 失败的请求白白消耗资源  

#### 适用场景

✅ 普通商品销售  
✅ 并发冲突率 < 10%  
✅ 不想用悲观锁  

---

### 方案三：Redis 缓存

#### 优点

✅ **性能极高** - 10000+ QPS 轻松达成  
✅ **响应快** - 毫秒级响应  
✅ **秒杀友好** - 专为高并发设计  
✅ **用户体验好** - 几乎无等待  
✅ **可扩展** - Redis 集群进一步提升  

#### 缺点

❌ **一致性弱** - Redis 和 MySQL 可能不一致  
❌ **实现复杂** - 需要处理数据同步、对账  
❌ **Redis 风险** - Redis 宕机数据丢失  
❌ **运维成本高** - 需要维护 Redis 集群、监控、备份  
❌ **开发成本高** - 17 人日开发量  
❌ **故障恢复复杂** - 需要处理缓存雪崩、穿透、击穿  

#### 适用场景

✅ 秒杀场景  
✅ QPS > 5000  
✅ 有 Redis 运维能力  
✅ 可接受最终一致性  

---

### 方案四：Redis 分布式锁

#### 优点

✅ **性能良好** - 800-1200 QPS  
✅ **强一致性** - 数据库保证准确  
✅ **分布式友好** - 天然支持多实例  
✅ **实现适中** - 基于 Redisson 简单  
✅ **平衡之选** - 性能和一致性兼顾  

#### 缺点

❌ **锁竞争** - 热门商品仍有瓶颈  
❌ **Redis 依赖** - Redis 故障影响业务  
❌ **需要降级** - Redis 故障时要降级到方案一  
❌ **锁超时问题** - 需要处理锁续期  

#### 适用场景

✅ 分布式部署  
✅ 500-1000 QPS  
✅ 需要强一致性  
✅ 已有 Redis 基础设施

## 超时释放机制对比

### 方案 A: Spring 定时任务

```java
@Scheduled(cron = "0 */5 * * * ?")
public void releaseExpiredStock() {
    // 扫描超时订单
}
```

#### 优点
✅ 实现简单，无需额外组件  
✅ Spring 内置支持  
✅ 快速上线  

#### 缺点
❌ 时效性差（最多延迟 5 分钟）  
❌ 扫描全表性能差  
❌ 单点故障风险  

---

### 方案 B: RabbitMQ 延迟消息

```java
// 发送延迟消息
message.setDelay(30 * 60 * 1000);  // 30 分钟

// 消费消息
@RabbitListener(queues = "order.timeout.queue")
public void checkOrderTimeout(Long orderId) {
    // 检查订单状态
}
```

#### 优点
✅ 时效性准确（秒级）  
✅ 不需要扫描全表  
✅ 消息可靠性高  
✅ 支持集群部署  

#### 缺点
❌ 需要引入 RabbitMQ  
❌ 增加运维复杂度  

---

### 方案 C: Redis Key TTL

```java
// 设置 30 分钟过期
redisTemplate.expire("order:" + orderId, 30, TimeUnit.MINUTES);

// 监听过期事件
@RedisListener
public void onKeyExpired(String key) {
    // 处理超时
}
```

#### 优点
✅ 时效性准确  
✅ Redis 内置功能  

#### 缺点
❌ Key 过期通知不可靠（可能丢失）  
❌ Redis 宕机数据丢失  
❌ 不推荐用于关键业务

## 最终建议

### 针对当前项目（无 Redis）

**第一选择**: **方案一**（MySQL 悲观锁）

**理由**:
1. ✅ 2-3 人日快速上线
2. ✅ 无需额外基础设施
3. ✅ 满足 500 QPS 以内场景
4. ✅ 为后续升级预留空间

**升级路径**:
- 流量达到 400 QPS → 准备方案四
- 有秒杀需求 → 研究方案三

---

### 针对高并发场景（1000+ QPS）

**第一选择**: **方案四**（Redis 分布式锁）

**理由**:
1. ✅ 性能满足 1000 QPS
2. ✅ 强一致性
3. ✅ 实现复杂度适中
4. ✅ 生产级方案

**特殊场景**:
- 秒杀活动 → 切换到方案三
- Redis 故障 → 降级到方案一
