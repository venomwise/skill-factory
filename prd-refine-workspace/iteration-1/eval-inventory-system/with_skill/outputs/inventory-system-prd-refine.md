## D1: 库存扣减的并发控制方案

**状态:** 已确认

### 问题来源

Review 报告 P0-1: "高并发下的库存超卖风险 - 多个用户同时下单同一商品,如何防止超卖?数据库层面是否使用行锁?乐观锁?悲观锁?"

### 问题分析

当前 PRD 只描述了库存扣减的业务规则,但未说明并发控制机制。在高并发场景下,如果多个请求同时读取到 stock=10,然后各自执行 stock-1,会导致最终 stock 不准确,造成超卖。

### 项目现状

- 使用 MySQL 存储库存
- 预占库存机制: reserved_stock 和 stock 需要同时更新
- 无 Redis 等分布式锁工具

### 方案分析

#### 方案 A: 数据库悲观锁(SELECT ... FOR UPDATE)

**实现方式:**
```sql
-- 查询并锁定行
SELECT stock FROM product_inventory WHERE product_id = ? FOR UPDATE;
-- 检查库存是否充足
IF stock > 0 THEN
  UPDATE product_inventory 
  SET stock = stock - 1, reserved_stock = reserved_stock + 1 
  WHERE product_id = ?;
END IF;
COMMIT;
```

**优点:**
- 实现简单,2 人日可完成
- 强一致性保证,事务内行级锁阻止并发修改
- 无需引入额外中间件,维护成本低
- 适合库存数据必须精确的场景

**缺点:**
- 锁等待会降低并发性能,热门商品会成为瓶颈
- 长事务会导致锁持有时间过长
- 在 1000 QPS + 热门商品场景下,可能出现锁等待排队

**风险:**
- 如果事务处理逻辑复杂(例如调用外部服务),锁持有时间会很长
- 数据库连接池可能被锁等待耗尽

**适用场景:**
- 普通商品,并发不高(单商品 QPS < 100)
- 对库存准确性要求极高
- 团队对 MySQL 事务熟悉

#### 方案 B: 数据库乐观锁(版本号机制)

**实现方式:**
```sql
-- 表结构增加 version 字段
ALTER TABLE product_inventory ADD COLUMN version INT DEFAULT 0;

-- 更新时检查版本号
UPDATE product_inventory 
SET stock = stock - 1, 
    reserved_stock = reserved_stock + 1,
    version = version + 1
WHERE product_id = ? AND version = ? AND stock > 0;

-- 如果 affected_rows = 0,说明版本冲突,需要重试
```

**优点:**
- 无锁等待,并发性能更好
- 适合读多写少的场景
- 失败时可以快速返回,由应用层控制重试

**缺点:**
- 冲突时需要重试,增加应用层复杂度(需要实现重试机制)
- 高并发下重试次数会增加,用户体验下降
- 需要修改数据库表结构,增加 version 字段

**风险:**
- 秒杀场景下重试风暴,可能导致大量请求失败
- 需要设置重试上限,避免无限重试

**适用场景:**
- 并发冲突不频繁的场景
- 可以接受部分请求失败重试
- 希望减少数据库锁等待

#### 方案 C: 原子化 UPDATE(基于 WHERE 条件)

**实现方式:**
```sql
-- 直接在 WHERE 条件中判断库存
UPDATE product_inventory 
SET stock = stock - 1, reserved_stock = reserved_stock + 1
WHERE product_id = ? AND stock > 0;

-- 检查 affected_rows 是否为 1
-- 如果为 0,说明库存不足或商品不存在
```

**优点:**
- 实现最简单,1 人日可完成
- 无需显式加锁,利用 MySQL 的行锁机制保证原子性
- 单条 SQL 完成,无需额外查询
- 性能适中,适合大多数场景

**缺点:**
- 无法区分"库存不足"和"商品不存在"(需要额外查询)
- 依赖数据库隔离级别(需要 REPEATABLE READ 或以上)

**风险:**
- 如果数据库隔离级别配置不当,可能出现幻读

**适用场景:**
- 对性能和实现复杂度都有要求
- 单商品并发 QPS < 500
- 团队希望快速上线,后续可优化

### 推荐方案

**推荐方案 C: 原子化 UPDATE**

**推荐理由:**

1. **实现成本低:** 1 人日可完成,无需修改表结构,无需实现复杂重试逻辑
2. **性能足够:** 在 1000 QPS 总量下,单商品并发通常不会太高,原子化 UPDATE 的性能可以满足
3. **可维护性好:** 单条 SQL 完成,代码简洁,团队理解成本低
4. **可演进:** 如果后续发现性能瓶颈,可以再引入 Redis 或其他优化方案

**方案对比总结:**

| 维度 | 方案 A 悲观锁 | 方案 B 乐观锁 | 方案 C 原子化 UPDATE |
|------|--------------|--------------|---------------------|
| 实现成本 | 2 人日 | 3 人日 | 1 人日 |
| 并发性能 | 中(有锁等待) | 高(冲突时需重试) | 中 |
| 一致性保证 | 强 | 强 | 强 |
| 复杂度 | 中 | 高 | 低 |
| 热门商品表现 | 锁等待排队 | 重试风暴 | 适中 |
| 推荐场景 | 极低并发 | 读多写少 | 通用场景 |

### 用户确认

**决策:** 采用方案 C(原子化 UPDATE)

**决策理由:**
- 实现成本最低,1 人日可快速上线
- 对于 1000 QPS 总量,性能足够满足需求
- 代码简洁,维护成本低,团队理解成本低
- 可演进,后续如有性能瓶颈可优化

**关键假设:**
- MySQL 隔离级别为 REPEATABLE READ(MySQL 默认级别)
- 单商品并发 QPS < 500
- 可接受"库存不足"和"商品不存在"统一提示

### 对 PRD 的影响

需要在 PRD 中补充:
1. **4.1 库存扣减规则** 章节增加并发控制说明
2. 明确使用原子化 UPDATE 语句保证并发安全
3. 说明依赖 MySQL 行锁机制和 REPEATABLE READ 隔离级别

## D2: 预占库存超时释放机制

**状态:** 已确认

### 问题来源

Review 报告 P0-2: "预占库存的超时释放机制缺失 - PRD 提到'订单超时未支付时回补库存',但超时时间是多久?如何检测超时订单?"

### 问题分析

当前 PRD 只描述了"订单超时未支付时回补库存",但未说明:
1. 超时时间是多久
2. 如何检测超时订单
3. 超时释放的可靠性保证

如果超时机制不完善,预占库存会永久锁死,导致可售库存虚高。

### 项目现状

- 使用 MySQL 存储库存数据
- 预占库存字段: reserved_stock
- 未描述订单系统的超时机制

### 方案分析

#### 方案 A: 定时任务扫描超时订单

**实现方式:**
- 订单表增加 created_at 字段
- 定时任务(如 Spring @Scheduled)每分钟扫描未支付订单
- 超时时间设为 30 分钟
- 扫描条件: status='待支付' AND created_at < NOW() - 30分钟

**优点:**
- 实现简单,2 人日可完成
- 无需引入额外中间件
- 超时时间可配置

**缺点:**
- 定时任务故障会导致库存永久锁死
- 扫描全表性能较差(订单量大时)
- 释放时间不精确(最多延迟 1 分钟)

**风险:**
- 单点故障风险,应用重启时定时任务停止
- 需要增加订单表索引(status, created_at)

#### 方案 B: 延迟消息队列(RabbitMQ/RocketMQ)

**实现方式:**
- 下单时发送延迟消息(延迟 30 分钟)
- 消息内容: 订单 ID
- 消费者检查订单状态,如果仍未支付则释放库存

**优点:**
- 精确到秒的超时控制
- 无需扫描全表,性能更好
- 消息队列保证可靠性

**缺点:**
- 需要引入消息队列中间件(开发 5 人日,运维成本增加)
- 系统复杂度提升
- 需要处理消息幂等性

**风险:**
- 如果消息队列故障,库存可能永久锁死
- 需要考虑消息丢失和重复消费

#### 方案 C: 定时任务 + 数据库状态机

**实现方式:**
- 订单表增加 timeout_at 字段(下单时设为 created_at + 30分钟)
- 定时任务每分钟扫描: status='待支付' AND timeout_at < NOW()
- 扫描时加索引: (status, timeout_at)
- 增加冗余检查:支付接口调用时也检查超时

**优点:**
- 实现成本适中,3 人日可完成
- 有索引支持,扫描性能较好
- 多层保障,可靠性较高

**缺点:**
- 仍依赖定时任务,有单点风险
- timeout_at 字段增加存储成本

**风险:**
- 需要保证 timeout_at 计算正确
- 时区问题可能导致超时判断错误

### 推荐方案

**推荐方案 C: 定时任务 + 数据库状态机**

**推荐理由:**

1. **成本适中:** 3 人日,无需引入新中间件
2. **性能足够:** 索引优化后,扫描性能可以满足中等订单量
3. **可靠性较好:** timeout_at 字段 + 支付接口双重检查
4. **可演进:** 未来订单量增长可升级到消息队列方案

**方案对比总结:**

| 维度 | 方案 A 定时扫描 | 方案 B 延迟消息 | 方案 C 状态机+定时 |
|------|----------------|----------------|-------------------|
| 实现成本 | 2 人日 | 5 人日 | 3 人日 |
| 超时精度 | 低(±1分钟) | 高(±1秒) | 低(±1分钟) |
| 性能 | 差(全表扫描) | 好 | 中(索引扫描) |
| 可靠性 | 低 | 高 | 中 |
| 运维成本 | 低 | 高 | 低 |

### 用户确认

**决策:** 采用方案 C(定时任务 + 数据库状态机)

**决策理由:**
- 成本适中,3 人日可完成
- 无需引入消息队列,降低系统复杂度
- 索引优化后性能可满足需求
- timeout_at 字段提升扫描效率,降低数据库压力

**关键假设:**
- 每日订单量 < 10 万单
- 可接受 ±1 分钟的超时精度
- 超时时间设为 30 分钟

### 对 PRD 的影响

需要在 PRD 中补充:
1. **4.1 库存扣减规则** 章节增加超时释放说明
2. **数据模型** 章节增加订单表 timeout_at 字段
3. 明确超时时间为 30 分钟
4. 说明使用定时任务检测超时订单
5. 增加索引要求: (status, timeout_at)

## D3: 性能优化方案 - 是否引入 Redis

**状态:** 已确认

### 问题来源

Review 报告 P1-3: "1000 QPS 的性能目标可行性存疑 - 当前方案是直接操作 MySQL,每次扣减都是一次数据库写操作,如果有热门商品(秒杀场景),数据库会成为瓶颈"

### 问题分析

PRD 要求"支持 1000 QPS",当前方案直接操作 MySQL:
1. 每次库存扣减都是数据库写操作
2. 热门商品会成为瓶颈
3. 是否需要引入 Redis 缓存

### 项目现状

- 未使用 Redis
- 性能目标: 1000 QPS
- 库存准确率要求: 100%

### 方案分析

#### 方案 A: 纯 MySQL 方案(不引入 Redis)

**实现方式:**
- 使用 D1 决策的原子化 UPDATE
- 数据库连接池优化(连接数、超时设置)
- 数据库索引优化
- 必要时增加数据库实例(主从复制,读写分离)

**优点:**
- 架构简单,无需引入新中间件
- 运维成本低
- 数据一致性天然保证

**缺点:**
- 热门商品仍会成为瓶颈
- 数据库扩展成本较高

**性能分析:**
- MySQL 单表单行更新 QPS 约 3000-5000(优化后)
- 1000 QPS 总量,如果分散到 100 个商品,单商品 QPS = 10,完全可行
- 如果出现热门商品(单商品 QPS > 500),会成为瓶颈

**适用场景:**
- 商品访问分散,无热门商品
- 团队不熟悉 Redis

#### 方案 B: Redis + MySQL 双写方案

**实现方式:**
- Redis 存储库存缓存
- 库存扣减先扣 Redis,再异步扣 MySQL
- Redis 使用 DECR 保证原子性

**优点:**
- Redis 单实例 QPS 可达 10 万+
- 热门商品性能大幅提升

**缺点:**
- 数据一致性问题(Redis 和 MySQL 可能不一致)
- 系统复杂度提升(需要处理同步失败)
- Redis 宕机时需要降级到 MySQL
- 开发成本 8 人日

**风险:**
- Redis 和 MySQL 数据不一致会导致超卖或少卖
- 需要实现数据对账和修复机制

**适用场景:**
- 有秒杀或热门商品场景
- 可接受最终一致性
- 团队有 Redis 运维能力

#### 方案 C: Redis 预加载 + MySQL 实时扣减

**实现方式:**
- 查询库存时从 Redis 读取(提升查询性能)
- 扣减库存时直接操作 MySQL(保证准确性)
- Redis 缓存定期刷新或失效时从 MySQL 加载

**优点:**
- 查询性能提升(Redis 读取)
- 扣减准确性保证(MySQL 写入)
- 数据一致性问题较小

**缺点:**
- 扣减性能未提升(仍受 MySQL 限制)
- 缓存失效时仍会打到 MySQL

**性能分析:**
- 如果查询 QPS >> 扣减 QPS,方案有效
- 如果扣减 QPS 高,方案无效

### 推荐方案

**推荐方案 A: 纯 MySQL 方案(不引入 Redis)**

**推荐理由:**

1. **性能足够:** 1000 QPS 总量,MySQL 单表可支撑
2. **架构简单:** 无需引入 Redis,降低运维成本
3. **数据准确:** 库存准确率 100% 的要求下,Redis 方案有一致性风险
4. **快速上线:** 无需学习和部署 Redis,节省 5 人日以上
5. **可演进:** 如果后续出现热门商品瓶颈,可按需引入 Redis

**何时需要引入 Redis:**
- 出现秒杀场景(单商品 QPS > 1000)
- 总 QPS 超过 5000
- 有热门商品导致数据库成为瓶颈

### 用户确认

**决策:** 采用方案 A(纯 MySQL 方案,不引入 Redis)

**决策理由:**
- 1000 QPS 总量,MySQL 性能足够
- 库存准确率 100% 要求下,Redis 有一致性风险
- 架构简单,降低运维成本和开发成本
- 可演进,后续按需引入 Redis

**关键假设:**
- 无秒杀场景或极端热门商品
- 商品访问相对分散
- 库存准确性优先级高于极致性能

### 对 PRD 的影响

需要在 PRD 中补充:
1. **非功能需求** 章节补充性能说明
2. 明确 1000 QPS 是总量,单商品并发预期 < 500 QPS
3. 说明暂不引入 Redis,使用 MySQL 直接存储
4. 补充未来演进方向:如出现秒杀场景,可引入 Redis

## D4: 分布式场景下的一致性保证

**状态:** 已确认

### 问题来源

Review 报告 P1-4: "分布式场景下的库存一致性 - 如果应用部署多个实例,如何保证库存扣减的全局一致性?是否需要分布式锁?"

### 问题分析

如果应用部署多个实例(分布式场景):
1. 多个实例同时扣减库存,如何保证一致性
2. 是否需要分布式锁

### 项目现状

- 使用 MySQL 存储库存
- D1 决策使用原子化 UPDATE
- 未使用 Redis

### 方案分析

#### 方案 A: 依赖 MySQL 行锁(无需分布式锁)

**实现方式:**
- 使用 D1 决策的原子化 UPDATE
- MySQL InnoDB 的行锁是跨实例生效的
- 多个应用实例同时 UPDATE 同一行,MySQL 会自动串行化

**原理说明:**
```sql
-- 实例 A 和实例 B 同时执行
UPDATE product_inventory 
SET stock = stock - 1, reserved_stock = reserved_stock + 1
WHERE product_id = 123 AND stock > 0;

-- MySQL 会使用行锁,自动保证串行执行
-- 只有一个实例的 UPDATE 会成功(如果库存只有 1)
```

**优点:**
- 无需任何额外工作
- MySQL 原生支持,天然保证分布式一致性
- 无需引入分布式锁中间件

**缺点:**
- 无

**风险:**
- 无(MySQL 行锁是成熟稳定的机制)

#### 方案 B: 引入分布式锁(Redis/Zookeeper)

**实现方式:**
- 扣减库存前先获取分布式锁
- 锁的 key 为: inventory_lock_{product_id}
- 扣减完成后释放锁

**优点:**
- 显式的锁控制,更容易理解

**缺点:**
- 需要引入 Redis 或 Zookeeper
- 增加系统复杂度和运维成本
- 锁超时、死锁等问题需要处理
- 开发成本 5 人日以上

**风险:**
- 分布式锁本身可能成为瓶颈
- 锁服务故障会导致业务不可用

### 推荐方案

**推荐方案 A: 依赖 MySQL 行锁(无需分布式锁)**

**推荐理由:**

1. **MySQL 行锁天然支持分布式一致性:** InnoDB 的行锁是数据库级别的,跨所有客户端连接生效
2. **无需额外开发:** D1 决策的原子化 UPDATE 已经足够
3. **无需引入新中间件:** 降低运维成本
4. **性能足够:** 行锁性能远超分布式锁

**分布式锁的误区:**
- 很多开发者认为"分布式场景需要分布式锁"
- 实际上,如果数据存储在数据库,数据库本身的锁机制就是分布式锁
- 只有数据存储在应用内存时,才需要外部分布式锁

### 用户确认

## PRD 更新预览

以下是将要写入 PRD 的修改内容:

### 2. 功能需求

**2.4 库存预警(新增)**
- 库存低于预警阈值时,在运营后台显示预警消息
- 预警阈值: 库存 < 10 件
- 定时任务每 30 分钟扫描一次
- 避免重复预警: 同一商品 24 小时内只预警一次

### 3. 数据模型

**3.1 商品库存表(补充)**
- product_id: 商品ID(主键)
- stock: 当前库存
- reserved_stock: 预占库存
- updated_at: 更新时间
- **索引:** PRIMARY KEY (product_id)
- **隔离级别要求:** REPEATABLE READ

**3.2 订单表(新增,用于超时释放)**
- order_id: 订单ID(主键)
- product_id: 商品ID
- status: 订单状态(待支付/已支付/已取消)
- created_at: 创建时间
- timeout_at: 超时时间(created_at + 30分钟)
- **索引:** INDEX idx_timeout (status, timeout_at)

**3.3 库存预警历史表(新增)**
- alert_id: 预警ID(主键)
- product_id: 商品ID
- stock: 库存数量
- alert_time: 预警时间
- **索引:** INDEX idx_product_time (product_id, alert_time)

### 4. 业务规则

**4.1 库存扣减规则(补充并发控制说明)**
- 下单时先预占库存(reserved_stock +1, stock -1)
- 支付成功后确认扣减(reserved_stock -1)
- 订单取消时释放预占(reserved_stock -1, stock +1)
- **并发控制:** 使用原子化 UPDATE 语句保证并发安全
  ```sql
  UPDATE product_inventory 
  SET stock = stock - 1, reserved_stock = reserved_stock + 1
  WHERE product_id = ? AND stock > 0;
  ```
- **一致性保证:** 依赖 MySQL InnoDB 行锁机制,支持分布式多实例部署
- **隔离级别要求:** REPEATABLE READ(MySQL 默认级别)

**4.1.2 超时释放机制(新增)**
- 超时时间: 30 分钟
- 检测方式: 定时任务每分钟扫描超时订单
- 扫描条件: status='待支付' AND timeout_at < NOW()
- 释放操作: reserved_stock -1, stock +1
- 冗余保障: 支付接口调用时也检查订单是否超时

**4.2 超卖防护(补充分布式说明)**
- 库存不足时拒绝下单
- stock >= 0
- **分布式一致性:** MySQL 行锁天然支持多实例部署,无需额外分布式锁
- **适用场景:** 单商品并发 QPS < 500

**4.3 库存预警规则(新增)**
- 预警阈值: stock < 10
- 检测频率: 定时任务每 30 分钟扫描一次
- 通知方式: 运营后台站内消息
- 防重通知: 同一商品 24 小时内只预警一次

### 5. 非功能需求(补充性能说明)

- 支持 1000 QPS(总量,单商品并发预期 < 500 QPS)
- 库存数据准确率 100%
- **技术架构:** 纯 MySQL 方案,不引入 Redis 或消息队列
- **数据库要求:** 
  - MySQL 8.0+
  - InnoDB 存储引擎
  - 隔离级别 REPEATABLE READ
- **扩展性:** 支持多实例水平扩展,依赖 MySQL 行锁保证一致性

**6. 未来演进(新增)**
- **秒杀场景:** 如出现单商品 QPS > 1000 的秒杀场景,可引入 Redis 预扣减方案
- **高并发优化:** 如总 QPS 超过 5000,可考虑读写分离或分库分表
- **预警增强:** 可增加邮件、短信等多渠道通知方式
- **超时优化:** 如订单量超过每日 10 万单,可升级为延迟消息队列方案
