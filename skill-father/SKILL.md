# Skill Father

创建新 skill 与审计现有 skill 的工作流技能。两种模式：

- **Mode A — 新建**：从意图捕获到 SKILL.md 落盘，含结构决策、路由设计、自审。
- **Mode B — 审计优化**：对已有 skill 做四维度体检（语体、一致性、陈旧内容、行为规则），产出修复方案。

本技能的核心资产是 [references/optimization-lessons.md](references/optimization-lessons.md)——从设计链技能（brainstorming / design-review / design-refine）的真实迭代中沉淀的失效模式库。**写之前和审之前都先读它**，其中每个模式都有症状、反例和修法。

## When to use

- 用户要把一个工作流/经验固化为新 skill
- 用户说"把这个流程变成 skill"（当前对话中已有可提取的工作流）
- 审计、优化、重写现有 skill 的任何文件
- 设计 skill 之间的路由边界与交接关系

## When not to use

- 只问技能规范、不动手产出 → 直接回答
- 修改的是普通项目代码而非 skill 文件 → 按常规开发流程

## Inputs / Outputs

**Inputs:**

- Mode A：用户的需求描述（可能模糊），或当前对话中待固化的工作流
- Mode B：目标 skill 的路径

**Outputs:**

- Mode A：完整的 skill 目录（`SKILL.md` + 按需的 `references/`、`assets/`、`scripts/`）
- Mode B：审计报告（四维度发现 + 分级修复方案），经用户确认后落盘的修改

## Workflow

### Mode A: Create

#### STEP 1: Capture intent

IF 当前对话中已包含待固化的工作流，THEN 先从对话历史提取：用过的工具、步骤顺序、用户纠正过的做法、观察到的输入输出格式，再让用户补空白项。否则逐项确认：

1. 这个 skill 让 agent 能做什么？（核心动作 + 产物）
2. 什么时候应该触发？（用户的真实说法，收集原话作触发词）
3. 什么时候**不**该触发？（与哪些现有技能相邻，边界在哪）
4. 期望的输出格式是什么？

全程一次只问一个问题（确认性问题也一样），每个问题带上你自己的几个理解作为选项供用户选择；IF 用户的回答里冒出新方向，THEN 顺势调整后面的问题。意图不明确，做再多都是徒劳，只会做多错多。

STOP when 你能用 2-3 句话说清这个 skill 的动作、触发条件和产物，且边界上没有悬而未决的模糊点。

#### STEP 2: Survey the ecosystem

新 skill 不是孤岛。在动笔前：

- 列出目标项目（或技能安装目录）中已有的 skill，确认没有功能重复；IF 有重叠，THEN 先与用户确认是新建、合并还是扩展
- 找出路由相邻的技能（上游从哪来、下游交给谁），明确交接点和各自的 "When not to use"
- IF 新技能会加入一条技能链，THEN 同步检查链上其他技能的路由描述是否需要更新

#### STEP 3: Design the structure

skill 的核心结构：

```
my-skill/
├── SKILL.md          # 必需：frontmatter 元数据（name + description）+ 正文指令
├── scripts/          # 可选：可执行代码——确定性、重复性的操作写成脚本
├── references/       # 可选：按需加载的文档——背景资料、清单、案例库
├── assets/           # 可选：产出用料——模板、样例、静态资源
└── ...               # 可按需添加其他文件或目录
```

**渐进式加载（progressive disclosure）是 skill 设计的命脉。** 上下文窗口由系统提示、对话历史、所有已安装技能的元数据和当前任务共享，是最稀缺的资源。skill 的内容因此分三层加载：

| 层     | 载体                                 | 加载时机      | 预算      |
| ------ | ------------------------------------ | ------------- | --------- |
| 元数据 | frontmatter（name + description）    | 始终在上下文  | 约 100 词 |
| 主体   | SKILL.md 正文                        | 技能触发时    | < 500 行  |
| 资源   | `references/`、`assets/`、`scripts/` | 按需读取/执行 | 不限      |

这套机制意味着：几十个技能可以同时安装，平时只各占约 100 词的 description；只有被触发的技能才付出正文成本；细节资料到真正用到时才进入上下文。**内容放得越靠前，成本越高**——把本该按需加载的内容写进正文，等于让每次触发都为它缴税。`scripts/` 最特殊：代码可以直接执行而不读入上下文，确定性、重复性的操作应固化为脚本，而不是写成长篇步骤说明。

结构决策问题（逐条过）：

1. 这段内容是 agent 推断不出来的吗？删掉它会完不成任务吗？示例展示的是 agent 推不出的模式吗？——三个都"否"就删
2. 这个操作 agent 能用 2-3 条命令直接完成吗？能就不要包 wrapper 脚本
3. 什么内容默认加载、什么按需加载？**按失效频率分配**：最常见、最危险的错误模式放 SKILL.md 主体，罕见路径放 `references/` 并在顶部放触发条件表
4. 多领域/多变体场景按变体组织 `references/`（如 `aws.md`、`gcp.md`），主体只放选择逻辑

#### STEP 4: Write SKILL.md

用 [assets/skill-template.md](assets/skill-template.md) 作骨架。写作时遵守以下硬规范（每条附正反例，详见"写作硬规范"一节）：

1. **name**：与目录名一致，仅小写字母/数字/连字符，1-64 字符，不以连字符开头结尾、不出现连续连字符
2. **description**：≤1024 字符，包含做什么 + 何时触发 + 触发词（用户原话）；倾向"pushy"以对抗欠触发；负向边界只按事实写，不设推测性禁止
3. **正文风格**：遵守 [references/language-style.md](references/language-style.md) 的语言风格规范（正文自然中文，英文仅作结构锚点，禁止句中夹杂）
4. **指令写法**：祈使句 + 说明理由；关卡写成编号检查清单且每条带 fallback；节奏规则与总量上限显式区分
5. **有产出物的技能**：为长寿命产物加保真规则（从一手来源恢复、禁止凭印象重建、禁止编造）

#### STEP 5: Self-audit

对照"审计清单"逐项自查，重点项展开见 [references/optimization-lessons.md](references/optimization-lessons.md)。发现问题回到 STEP 4 修改，直到清单全绿。

### Mode B: Audit & optimize

#### STEP 1: Load the skill

读目标 skill 的全部文件（SKILL.md + references + assets），并读 git 历史理解演进脉络：每次修改是失败驱动的补丁还是凭空的添加。

#### STEP 2: Audit four dimensions

按四个维度逐一检查（清单见"审计清单"，案例见 optimization-lessons.md）：

1. **语体一致性**：有无句中夹杂、翻译腔、同文件内风格分裂
2. **一致性**：跨文件术语/字段标签/路径约定是否对齐；路由引用的技能是否存在；与链上相邻技能的交接是否闭环
3. **陈旧内容**：被上游删除的约定是否残留；引用的章节名/路径是否仍有效
4. **行为规则**：关卡有无 fallback；油门指令有无配平；记法前缀是否冲突；有无关卡缺失导致竞态

#### STEP 3: Report and confirm

输出分级发现清单（语义损失 > 行为缺陷 > 语体问题），每条附证据位置和具体修法。**等用户确认后再动手**，不直接改文件。

#### STEP 4: Apply and verify

修改落盘后做语义完备性检查：IF 涉及重写，THEN 用 diff 或 `git log -S` 逐一确认旧版本中的每条行为规则在新版本中有对应承载，防止静默丢失。

## 写作硬规范

### description 写作

做什么 + 何时触发 + 触发词（用户原话），三者缺一不可。负向边界只按事实写：只有实际发生过误触发或误用，才补一条防线；不要预先写推测性的禁止——过分强调未出现的错误，本身就是对路由信号的污染。

```
✅ 好：对 design.md 进行批判性评审并写入 review.md 裁决报告。当用户想评审设计文档、
做质量关卡，或检查完整性、盲点、过度设计时调用。触发词包括"评审设计"、"review design"、
"检查设计文档"。

❌ 坏：帮助你完成设计相关的工作。（无触发动作、无触发词，必然欠触发）
```

### 意图优先

任何技能的工作流，第一个环节都应该是"探索背景与边界、确认意图"。意图不明确，做再多都是徒劳，只会做多错多；弄清楚意图与边界后再动手，才能事半功倍。编写工作流时遵守：

- 发现分歧或模糊的点，主动停下来询问，不要基于假设硬往前推
- 问题带上你自己的几个理解作为选项，多选优于让用户自己输入——选项也能启发用户加深自己的理解
- 一次只问一个问题，确认性的问题也一样：用户随时可能冒出新想法或新要求，一个个问，后面的问题才能跟着答案及时调整

```
✅ 好：这一点我有两种理解：A 是……，B 是……，我倾向 A，因为它更接近你前面说的场景。
      你想要哪种？（一次一问、带选项、有自己的立场）

❌ 坏：请提供以下信息以便继续：1) 目标用户 2) 性能要求 3) 预算 4) 上线时间。
      （一次问一堆、无选项、无立场，用户答完也很难再补充新想法）
```

### 关卡与检查清单

关卡写成编号清单，每条检查项带"不满足时回哪"的 fallback。

```
✅ 好：
1. 本次会话中是否至少问过用户一个澄清性问题？If no，回到 STEP 4。
2. 用户能陈述想要什么、为什么、明确不要什么吗？If no，回到 STEP 4 继续提问。

❌ 坏：在进入下一步之前，确保已经充分理解了用户的需求。（prose 关卡无法自检，无 fallback）
```

### 节奏与上限

凡"每轮一个"类节奏规则，显式声明它不是总量上限。

```
✅ 好：每轮只问一个问题并等待答案——这是节奏控制，不是对总提问数的限制；
持续提问直到退出条件满足。

❌ 坏：One question at a time.（会被执行为"问完一个就收尾"）
```

### 油门与刹车配对

有"持续做直到 X"的油门指令，就要配"简单场景允许压缩"的刹车许可，否则琐碎输入被过度处理。

### 记法命名空间

同一上下文内一个前缀只允许一个含义；需要经受重排/恢复的标识用"标题 + 来源编号"这类稳定标识，不用序号。

### 产物保真

长寿命产物（写盘文档、决策记录）的内容必须从一手来源恢复：

```
✅ 好：Decision Record 必须从实际讨论中恢复；IF 内容已滚出近期对话，THEN 回头重读
对话原文并如实恢复，不要凭印象重建，不要编造未讨论过的内容。

❌ 坏：记录讨论过的方案。（模型会凭压缩后的印象"重建"，细节漂移且看似合理）
```

## 审计清单

Mode B 逐项执行，Mode A 在 STEP 5 自查：

**语体**

- [ ] 无句中夹杂（中文句子里嵌英文动词/分句）
- [ ] 无翻译腔（逐词对译的晦涩表达）
- [ ] 同一文件内文体一致；结构性英文（标题、枚举、路径、技能名）与正文中文分工清晰

**一致性**

- [ ] 跨文件的术语、字段标签、枚举值完全对齐
- [ ] 路由引用的技能/工具在目标环境中存在（无死路由）
- [ ] 与相邻技能的交接闭环：本技能的输出路由与对方的输入声明匹配
- [ ] 引用的章节名、路径约定与上游模板一致

**陈旧内容**

- [ ] 无上游已删除约定的残留（用 `git log -S` 抽查关键短语的增删历史）
- [ ] 降级路径、豁免条件等边界规则仍然存在且自洽

**行为规则**

- [ ] 工作流以"探索背景与边界、确认意图"开篇；意图不清不动手
- [ ] 提问一次一个、带自己的理解作选项（多选优于自由输入）
- [ ] 每个关卡是编号清单且每条有 fallback
- [ ] 油门指令有刹车配平
- [ ] 记法前缀无冲突
- [ ] 昂贵动作（写盘、实施、调用下游）前有确认关卡
- [ ] 无模型无法评估的伪精确规则（如"保持稳定 2 轮"这类无操作定义的阈值）
- [ ] 无推测性的禁止条款：每条明确禁止都对应实际发生过的错误，一切以事实为准
- [ ] 长寿命产物有保真规则

**结构**

- [ ] SKILL.md < 500 行；超限时内容向 `references/` 分层并有清晰指针
- [ ] > 300 行的 reference 有目录；每个 reference 注明何时读
- [ ] 反例按失效频率分配：高频危险反例在主体默认加载，罕见路径按需

## Verification

- [ ] Mode A：产出目录包含 SKILL.md，frontmatter 的 name 与目录名一致且符合命名规则
- [ ] Mode A：description 含动作、触发条件、触发词三要素；如有负向边界，均基于实际发生过的误触发/误用
- [ ] Mode A：STEP 5 自审清单全绿
- [ ] Mode B：审计覆盖四维度，每条发现有证据位置和修法
- [ ] Mode B：重写类修改做过语义完备性检查（`git log -S` 或逐条 diff 对照）
- [ ] 所有产出文件符合语言风格规范（见 `references/language-style.md`）

## Safety & guardrails

- **无惊讶原则**：skill 内容不得包含恶意代码、漏洞利用或误导性行为；拒绝创建设计用于未授权访问或数据外泄的技能。角色扮演类技能可以接受。
- **先方案后动手**：Mode B 的修改必须先呈现发现与修法，获得用户确认后才改文件。
- **不过拟合**：从测试用例获得反馈时泛化修改，不为单个用例加特殊分支；发现自己在写全大写 ALWAYS/NEVER 时，改为解释理由。
- **保持精简**：每段内容过三问（推断不出？删了完不成？示例不可替代？），全"否"则删。
