# Skill Father

创建新 skill 与审计现有 skill 的工作流技能。两种模式：

- **Mode A — 新建**：从确认意图到写入 SKILL.md，包含结构决策、路由设计和自审。
- **Mode B — 审计优化**：对已有 skill 做四维度体检（语体、一致性、陈旧内容、行为规则），产出修复方案。

本技能的核心资产是
[references/optimization-lessons.md](references/optimization-lessons.md)——从设计链技能
（clarifying / design-review / design-refine）的真实迭代中整理出的失效模式库。
**写之前和审之前都先读它**，其中每个模式都有症状、反例和修法。

## When to use

- 用户要把一个工作流/经验固化为新 skill
- 用户说"把这个流程变成 skill"（当前对话中已有可提取的工作流）
- 审计、优化、重写现有 skill 的任何文件
- 设计 skill 之间的路由边界与交接关系

## When not to use

- 只问技能规范、不动手产出 → 直接回答
- 修改的是普通项目代码而非 skill 文件 → 按常规开发流程

## Inputs / Outputs

**Inputs:**

- Mode A：用户的需求描述（可能模糊），或当前对话中待固化的工作流
- Mode B：目标 skill 的路径

**Outputs:**

- Mode A：完整的 skill 目录（`SKILL.md` + 按需的 `references/`、`assets/`、`scripts/`）
- Mode B：审计报告（四维度发现 + 分级修复方案），以及用户确认后写入文件的修改

## Workflow

### Mode A: Create

#### STEP 1: Capture intent

IF 当前对话中已包含待固化的工作流，THEN 先从对话历史提取：用过的工具、步骤顺序、用户纠正过的做法、观察到的输入输出格式，再让用户补空白项。否则逐项确认：

1. 这个 skill 让 agent 能做什么？（核心动作 + 产物）
2. 什么时候应该触发？（用户的真实说法，收集原话作触发词）
3. 什么时候**不**该触发？（与哪些现有技能相邻，边界在哪）
4. 期望的输出格式是什么？

全程一次只问一个问题（确认性问题也一样），每个问题带上你自己的几个理解作为选项供用户选择；IF 用户的回答里冒出新方向，THEN 顺势调整后面的问题。意图不明确，做再多都是徒劳，只会做多错多。

STOP when 你能用 2-3 句话说清这个 skill 的动作、触发条件和产物，且边界上没有悬而未决的模糊点。

#### STEP 2: Survey the ecosystem

新 skill 不是孤岛。在动笔前：

- 列出目标项目（或技能安装目录）中已有的 skill，确认没有功能重复；IF 有重叠，THEN 先与用户确认是新建、合并还是扩展
- 找出路由相邻的技能（上游从哪来、下游交给谁），明确交接点和各自的 "When not to use"
- IF 新技能会加入一条技能链，THEN 同步检查链上其他技能的路由描述是否需要更新

#### STEP 3: Design the structure

skill 的核心结构：

```
my-skill/
├── SKILL.md          # 必需：frontmatter 元数据（name + description）+ 正文指令
├── scripts/          # 可选：可执行代码——确定性、重复性的操作写成脚本
├── references/       # 可选：按需加载的文档——背景资料、清单、案例库
├── assets/           # 可选：产出用料——模板、样例、静态资源
└── ...               # 可按需添加其他文件或目录
```

**渐进式加载（progressive disclosure）决定 skill 占用多少上下文。** 上下文窗口由系统提示、
对话历史、所有已安装技能的元数据和当前任务共享。skill 的内容因此分三层加载：

| 层     | 载体                                 | 加载时机      | 预算      |
| ------ | ------------------------------------ | ------------- | --------- |
| 元数据 | frontmatter（name + description）    | 始终在上下文  | 约 100 词 |
| 主体   | SKILL.md 正文                        | 技能触发时    | < 500 行  |
| 资源   | `references/`、`assets/`、`scripts/` | 按需读取/执行 | 不限      |

这套机制意味着：几十个技能可以同时安装，平时只各占约 100 词的 description；只有被触发的
技能才加载正文，细节资料到真正需要时才进入上下文。内容放得越靠前，每次触发占用的上下文
越多。`scripts/` 最特殊：代码可以直接执行而不读入上下文，确定性、重复性的操作应固化为
脚本，而不是写成长篇步骤说明。

结构决策问题（逐条过）：

1. 这段内容是 agent 推断不出来的吗？删掉它会完不成任务吗？示例展示的是 agent 推不出的模式吗？——三个都"否"就删
2. 这个操作 agent 能用 2-3 条命令直接完成吗？能就不要包 wrapper 脚本
3. 什么内容默认加载、什么按需加载？**按失效频率分配**：最常见、最危险的错误模式放 SKILL.md 主体，罕见路径放 `references/` 并在顶部放触发条件表
4. 多领域/多变体场景按变体组织 `references/`（如 `aws.md`、`gcp.md`），主体只放选择逻辑

#### STEP 4: Write SKILL.md

用 [assets/skill-template.md](assets/skill-template.md) 作骨架。写作时遵守以下硬规范（每条附正反例，详见"写作硬规范"一节）：

1. **name**：与目录名一致，仅小写字母/数字/连字符，1-64 字符，不以连字符开头结尾、不出现连续连字符
2. **description**：≤1024 字符，包含做什么 + 何时触发 + 触发词（用户原话）；倾向"pushy"以对抗欠触发；负向边界只按事实写，不设推测性禁止
3. **正文风格**：遵守 [references/language-style.md](references/language-style.md) 的语言风格规范（正文自然中文，英文仅作结构锚点，禁止句中夹杂）
4. **指令写法**：祈使句 + 说明理由；关卡写成编号检查清单且每条带 fallback；节奏规则与总量上限显式区分
5. **有产出物的技能**：为写入文件或会被后续流程读取的内容添加来源核对规则
   （重新读取原始资料并据此填写，不凭记忆补写或编造）
6. **生成或修改文档的技能**：内置可独立执行的文档语言关卡；写完后重新读取实际文件，
   在不改变事实、决策、状态和技术含义的前提下检查表达，并重新运行结构与格式验证
7. **边界写法**：先定义默认产物、唯一来源、状态出口、升级条件和验证方式，再补充必要的事实型
   guardrail；不要把每个失败场景改写成一条孤立的“不要/禁止/不能”提示

#### STEP 5: Self-audit

重新读取实际生成的 `SKILL.md`、`assets/` 和 `references/`，对照“审计清单”逐项自查。
先检查这些文件自身的表达，再检查产出型 skill 是否内置文档语言关卡。重点项展开见
[references/optimization-lessons.md](references/optimization-lessons.md)。发现问题回到 STEP 4
修改，直到清单全绿。

### Mode B: Audit & optimize

#### STEP 1: Load the skill

读目标 skill 的全部文件（SKILL.md + references + assets），并读 git 历史理解演进脉络：每次修改是失败驱动的补丁还是凭空的添加。

#### STEP 2: Audit four dimensions

按四个维度逐一检查（清单见"审计清单"，案例见 optimization-lessons.md）：

1. **语体一致性**：有无句中夹杂、翻译腔、同文件内风格分裂；生成文档的技能是否只约束
   对话语气，却没有检查实际写入的正文
2. **一致性**：跨文件术语、字段标签和路径约定是否一致；路由引用的技能是否存在；
   与相邻技能的输入和输出能否互相对应
3. **陈旧内容**：被上游删除的约定是否残留；引用的章节名/路径是否仍有效
4. **行为规则**：关卡有无 fallback；持续执行规则是否有对应的简化条件；
  记法前缀是否冲突；生成文档后是否重新读取实际文件；有无关卡缺失导致竞态；
  默认行为是否由正向契约定义，而不是由负面提示词清单拼接

#### STEP 3: Report and confirm

输出分级发现清单（语义损失 > 行为缺陷 > 语体问题），每条附证据位置和具体修法。**等用户确认后再动手**，不直接改文件。

#### STEP 4: Apply and verify

修改写入文件后重新读取实际文件，先检查表达是否自然，再逐条确认规则没有遗漏。
IF 涉及重写，THEN 使用 diff 或 `git log -S` 检查旧版本中的每条行为规则在新版本中仍有
对应说明；语言调整后重新运行原有结构与格式验证。

## 写作硬规范

### description 写作

做什么 + 何时触发 + 触发词（用户原话），三者缺一不可。负向边界只按事实写：只有实际发生过误触发或误用，才补一条防线；不要预先写推测性的禁止——过分强调未出现的错误，本身就是对路由信号的污染。

```
✅ 好：对 design.md 进行批判性评审并写入 review.md 裁决报告。当用户想评审设计文档、
做质量关卡，或检查完整性、盲点、过度设计时调用。触发词包括"评审设计"、"review design"、
"检查设计文档"。

❌ 坏：帮助你完成设计相关的工作。（无触发动作、无触发词，必然欠触发）
```

### 正向边界，避免负面提示词堆叠

负面提示词不是行为设计的替代品。每遇到一次偏差就追加一条“不要/禁止/不能”，会让 skill 变成
越来越长的例外清单；Agent 可能只规避字面命中，却仍不知道默认应产出什么、信息以哪里为准、何时升级或
何时结束。

先按以下顺序定义行为契约：

1. **Canonical output**：默认产出是什么，产物由哪些文件、字段或状态组成。
2. **Source of truth**：每项内容以哪个输入、章节、事实或上游产物为准。
3. **Default route**：正常完成后进入哪个状态或下游；哪些简单场景可以缩短流程。
4. **Escalation boundary**：哪些可观察的变化触发人工确认、范围化复核或更高风险流程。
5. **Validation**：用结构、引用、命令、测试结果或可观察状态证明契约已经满足。

只有实际发生过且能够复现的误触发或误用，才补充负向 guardrail。每条 guardrail 必须同时说明：
触发证据、替代行为和不满足时的 fallback；安全、合规或权限类硬约束可以保留明确禁止，但仍应说明
合规路径和验证方式。多个 guardrail 若都在表达同一边界，应合并到一个契约或状态规则中。

```
❌ 坏：不要生成临时产物，不要重复检查，不要跳过确认，不要把内部信息带入下游。
✅ 好：下游只读取 canonical artifact；流程按变更边界选择默认出口或升级复核；写入前完成来源核对，
      写入后用结构和引用检查验证，无法满足时回到对应决策步骤。
```

审计时问：删去某条负向提示后，Agent 是否仍能从正向契约推导出正确行为？如果不能，缺的是产物、
状态或验证定义，而不是更多禁止句子。

### 意图优先

任何技能的工作流，第一个环节都应该是"探索背景与边界、确认意图"。意图不明确，做再多都是徒劳，只会做多错多；弄清楚意图与边界后再动手，才能事半功倍。编写工作流时遵守：

- 发现分歧或模糊的点，主动停下来询问，不要基于假设硬往前推
- 问题带上你自己的几个理解作为选项，多选优于让用户自己输入——选项也能启发用户加深自己的理解
- 一次只问一个问题，确认性的问题也一样：用户随时可能冒出新想法或新要求，一个个问，后面的问题才能跟着答案及时调整

```
✅ 好：这一点我有两种理解：A 是……，B 是……，我倾向 A，因为它更接近你前面说的场景。
      你想要哪种？（一次一问、带选项、有自己的立场）

❌ 坏：请提供以下信息以便继续：1) 目标用户 2) 性能要求 3) 预算 4) 上线时间。
      （一次问一堆、无选项、无立场，用户答完也很难再补充新想法）
```

### 关卡与检查清单

关卡写成编号清单，每条检查项带"不满足时回哪"的 fallback。

```
✅ 好：
1. 本次会话中是否至少问过用户一个澄清性问题？IF 否，THEN 回到 STEP 4。
2. 用户能陈述想要什么、为什么、明确不要什么吗？IF 否，THEN 回到 STEP 4 继续提问。

❌ 坏：在进入下一步之前，确保已经充分理解了用户的需求。（prose 关卡无法自检，无 fallback）
```

### 节奏与上限

凡"每轮一个"类节奏规则，显式声明它不是总量上限。

```
✅ 好：每轮只问一个问题并等待答案——这是节奏控制，不是对总提问数的限制；
持续提问直到退出条件满足。

❌ 坏：One question at a time.（会被执行为"问完一个就收尾"）
```

### 持续执行与简化条件

要求“持续执行直到 X”时，同时说明哪些简单场景允许简化流程，避免小任务被过度处理。

### 记法命名空间

同一上下文内一个前缀只允许一个含义；需要经受重排/恢复的标识用"标题 + 来源编号"这类稳定标识，不用序号。

### 内容来源核对

写入文件或会被后续流程读取的内容必须重新读取原始资料并据此填写：

```
✅ 好：Decision Record 必须依据实际讨论填写；IF 内容已滚出近期对话，THEN 重新读取
对话原文，不要凭记忆补写，也不要编造未讨论过的内容。

❌ 坏：记录讨论过的方案。（模型可能只凭压缩后的记忆补写，细节会悄悄变化）
```

### 产出文档的语言关卡

会生成或修改 Markdown、设计、评审、计划或其他供人阅读文档的 skill，必须在工作流末尾
加入可自检的语言关卡。不能只写“输出自然、直接”，因为它容易只约束最终回复。

关卡至少包含：

1. 重新读取实际写入的文件，而不是依赖生成时的印象。
2. 中文正文使用自然、具体的表达；英文只保留技术术语、固定字段、路径、ID、枚举和章节名。
3. 抽象说法能回答“谁做什么、什么条件下发生、结果是什么、以什么为准”；不能回答时改写。
4. 不机械替换词语；根据上下文处理逐词翻译、商业黑话、流程隐喻、模板化开场和空泛总结。
5. 数字、事实、责任主体、用户决定、状态、ID、路径、命令、代码、引用和技术术语保持不变。
6. 语言修改不得新增、删除、弱化或扩大需求、风险、finding、Decision 或 Acceptance Criteria。
7. 修改后重新运行该 skill 原有的结构、追踪关系、状态和格式检查。

核心关卡必须写在产出型 skill 自身，不把另一个文风 skill 作为必需依赖。完整设计原则和
误改边界见 [语言风格规范](references/language-style.md)。

## 审计清单

Mode B 逐项执行，Mode A 在 STEP 5 自查：

**语体**

- [ ] 无句中夹杂（中文句子里嵌英文动词/分句）
- [ ] 无翻译腔（逐词对译的晦涩表达）
- [ ] 同一文件内文体一致；结构性英文（标题、枚举、路径、技能名）与正文中文分工清晰
- [ ] 生成或修改文档的 skill 已区分对话语气和文件正文，并要求重新读取实际产物

**一致性**

- [ ] 跨文件的术语、字段标签、枚举值完全对齐
- [ ] 路由引用的技能/工具在目标环境中存在（无死路由）
- [ ] 与相邻技能的输入和输出互相对应
- [ ] 引用的章节名、路径约定与上游模板一致

**陈旧内容**

- [ ] 无上游已删除约定的残留（用 `git log -S` 抽查关键短语的增删历史）
- [ ] 降级路径、豁免条件等边界规则仍然存在且自洽

**行为规则**

- [ ] 工作流以"探索背景与边界、确认意图"开篇；意图不清不动手
- [ ] 提问一次一个、带自己的理解作选项（多选优于自由输入）
- [ ] 每个关卡是编号清单且每条有 fallback
- [ ] 持续执行规则有对应的简化条件
- [ ] 记法前缀无冲突
- [ ] 昂贵动作（写文件、实施、调用下游）前有确认关卡
- [ ] 无模型无法评估的伪精确规则（如"保持稳定 2 轮"这类无操作定义的阈值）
- [ ] 默认行为由 canonical output、source of truth、状态出口和 validation 定义，而不是由负面提示词清单拼接
- [ ] 每条负向 guardrail 都有实际误用证据、替代行为和 fallback；重叠边界已合并
- [ ] 无推测性的禁止条款：每条明确禁止都对应实际发生过的错误，一切以事实为准
- [ ] 写入文件或会被后续流程读取的内容已设置来源核对规则
- [ ] 文档语言关卡保护事实、决策、状态、ID 和技术术语，不采用机械禁词替换
- [ ] 文档语言调整后会重新运行结构、追踪关系、状态和格式检查

**结构**

- [ ] SKILL.md < 500 行；超限时内容向 `references/` 分层并有清晰指针
- [ ] > 300 行的 reference 有目录；每个 reference 注明何时读
- [ ] 反例按失效频率分配：高频危险反例在主体默认加载，罕见路径按需

## Safety & guardrails

- **安全边界**：skill 内容不得包含恶意代码、漏洞利用或误导性行为；拒绝创建设计用于
  未授权访问或数据外泄的技能。角色扮演类技能可以接受。
- **先方案后动手**：Mode B 的修改必须先呈现发现与修法，获得用户确认后才改文件。
- **不过拟合**：从测试用例获得反馈时泛化修改，不为单个用例加特殊分支；发现自己在写全大写 ALWAYS/NEVER 时，改为解释理由。
- **保持精简**：每段内容过三问（推断不出？删了完不成？示例不可替代？），全"否"则删。
