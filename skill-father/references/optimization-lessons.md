# Skill 优化失效模式库

从技能的真实迭代中整理而来。每个模式按“症状 → 反例 → 修法”组织，写新技能和审计
现有技能时对照使用。反例必须脱离上下文也能读懂：描述事件的形态，不依赖特定项目名、
会话编号或只有当事人才懂的引用。

## 触发与路由

### P1 触发面扩大

**症状**：description 扩大触发范围（如把 bug 修复纳入设计类技能）。description 是技能路由的第一杠杆，改它的收益和风险都被放大，过触发风险随触发面同步增长。

**反例**：description 写"在进行功能开发、bug 修复、优化处理时调用"，正文 "When not to use" 却写"有明确根因的 bug 修复不适用"——两者矛盾，而路由器只看 description。

**修法**：谨慎扩大触发面，确保 description 与正文 "When not to use" 一致。防线只按事实写：实际发生过过触发之后，再基于事实收窄；不要预先添加推测性的防线。

### P2 死路由

**症状**："When not to use" 或路由指引指向目标环境中不存在的技能名。

**反例**：`代码评审 → route to code-review / review`——运行环境里没有这两个技能，agent 照做会悬空。

**修法**：写路由前核实目标技能存在；不确定存在性时改为能力描述："代码级评审不在本技能范围内，应交回相应的评审工具"。

### P3 路由交接不完整

**症状**：A 技能规定某情形交给 B，B 技能的收尾却没有把该情形送回来。链条在特定路径上断裂。

**反例**：design-review 规定 Reject 裁决要在 refine 后重跑评审；但 design-refine 的收尾只写"设计完备则进入 spec-plan"，Reject 来源的 refine 走完就丢了复审环节。

**修法**：画一遍技能链的完整状态机，每条边从两端各查一次：A 说"交给 B"的情形，B 是否有对应的入口声明和出口路由。

## 对话控制

### P4 技术细节误判为意图确认

**症状**：用户的请求充满技术术语，agent 就跳过澄清直接开干。熟悉技术词汇不等于知道用户想要什么——意图、优先级、取舍偏好只存在于用户头脑中，无法通过检查项目获得。

**修法**：在准入门槛中明确说明：“请求在技术上很详细，不代表意图已经确认”；把
“本次会话是否至少问过一个澄清性问题”列为硬性检查项。提问一次一个，并提供自己的
几个理解供用户选择；选项既降低用户回答成本，也能帮助用户继续明确需求。

### P5 自问自答

**症状**：agent 提出问题后不等回答，同一轮里用假设替用户作答继续推进。

**修法**：显式指令"提出问题后停下等待回答，不要用假设代替用户作答"，并说明理由：意图、优先级、验收标准属于只能问、不能猜的信息。

### P6 节奏规则误读为总量上限

**症状**："一次只问一个问题"被执行成"总共只问一个问题"。

**修法**：节奏规则必须自带边界声明："这是节奏控制，不是总量上限；持续提问直到退出条件满足"。

### P7 伪精确阈值

**症状**：给退出条件加模型无法可靠评估的数值阈值，如"问题陈述在最近 2 轮交流中保持稳定"。模型既无法度量"稳定"，又可能被它强制多问一轮，或干脆忽略。

**修法**：退出条件要可自检——改成"你能用用户的原话在 2-3 句话内总结其意图、优先级和约束吗？"这类操作性测试。写不出操作定义的阈值就不要写。

## 流程结构

### P8 prose 关卡无 fallback

**症状**：进入条件写成一段话（"确保已充分理解需求后再继续"），模型无法自检，跳过了也没人知道。

**修法**：关卡写成编号检查清单，每条给"不满足时回哪"的明确动作：

```
1. 是否至少问过一个澄清性问题？IF 否，THEN 回到 STEP 4。
2. 用户能陈述想要什么、为什么、不要什么吗？IF 否，THEN 回到 STEP 4 继续提问。
```

### P9 昂贵动作前缺确认关卡

**症状**：写文件、实施、调用下游技能等昂贵或难撤销动作前没有用户确认，反馈和动作之间
出现竞态：agent 给出方案后立刻执行，用户来不及反对。

**修法**：每个昂贵动作前设"呈现 → 等待确认 → 执行"关卡，并写明反馈分流：同意则执行；提出反馈则先判断反馈是否改变意图或方案，再决定就地更新还是回退重做。

### P10 持续执行缺少简化条件

**症状**：流程要求“持续提问直到满足条件”“逐项处理每个发现”，却没有说明简单场景
何时允许简化。结果是小任务也被迫走完全部流程。

**修法**：为每条持续执行规则补充可判断的简化条件，例如：“简单明确的请求允许在少数
几轮内完成，不要为凑流程追加环节”。持续条件和简化条件都必须能够自检。

### P11 记法前缀冲突

**症状**：同一上下文里"D1"既指决策队列序号又指评审维度编号，读者（和模型）必然混淆。序号还有第二个缺陷：队列重排、条目恢复、合并都会使序号漂移，历史引用指向错误条目。

**修法**：一个前缀在一个上下文内只允许一个含义。finding 使用与严重性无关的稳定 ID，
例如 `F-001`；Severity、Origin、轮次和状态分别存储。需要经受队列重排的决策项使用
“标题 + 来源 finding”标识，例如 `错误处理策略（来源: F-003, F-005）`。

### P17 评审-修复循环不收敛

**症状**：评审和修复围绕同一份反复修订的文档迭代，每轮都出现“新”问题，Decision
和 Closure 持续膨胀。常见原因包括：每轮重新执行开放式全量评审；finding 身份与严重性
耦合；refine 把每个 finding 都追加为 Decision；修复内容没有传播到 AC、Data Flow、
Error Handling 和 Testing；评审时 Verdict 与 refine 后 readiness 混在同一视图。

**反例**：某设计在 R3 有 6 条 finding，R4 变为 8 条，其中既有延续和重新打开，
也有 reviewer 前轮漏检。报告只统计“新增”，没有说明问题由 refine 引入、依赖解锁、
基线漏检还是项目事实变化；design 则为每条 finding 追加 Decision 和 Revised 历史。

**修法**：首轮执行 Full Review，完成全部维度后确定本轮 finding 集合；refine 后默认执行
Closure Review，只检查旧 finding、changed sections 和 Impact matrix 中预先列出的关联章节。
Closure 新 finding 必须声明
`refine-regression`、`dependency-unlocked`、`baseline-miss` 或 `context-change`，并提供因果证据。
finding 使用稳定 `F-###`，Severity 独立。只有持久且非显然的选择进入语义 `DR-*`；
Direct repair 只更新设计章节。用户明确驳回且可能重复出现的 concern 写入带
`Rejected concern` 和 `Revisit when` 的边界 Decision。出口条件是 Current Readiness
为 `ready / Go`，而不是零 finding。

### P19 负面提示词堆叠

**症状**：每次发现 Agent 偏离预期，就在 skill 末尾追加一条“不要/禁止/不能”。规则数量增长，
但默认产物、来源、状态出口和升级条件仍然没有被定义；不同负面条款还可能互相重叠或冲突。

**反例**：某个文档生成 skill 先后加入“不要复制原文”“不要生成额外章节”“不要重复校验”“不要
跳过用户确认”等提示。Agent 仍会漏掉必要的来源引用和验证步骤，因为这些提示只描述了不应发生什么，
没有说明 canonical artifact 应包含什么、何时需要确认以及完成后如何判断通过。

**修法**：把经验抽象成正向契约，而不是继续扩展禁止清单：

1. 定义默认产物集合及其唯一来源；下游只读取这套 canonical artifact。
2. 定义正常状态出口和简化路径；把跨组件、行为或风险边界的变化映射到升级流程。
3. 定义可观察的 validation，用结构、引用、命令、测试或状态证明完成条件。
4. 只有有证据的重复误用才保留最小负向 guardrail，并配套替代行为和 fallback。
5. 对安全、合规和权限类硬约束保留明确限制，同时给出允许的合规路径和验证方式。

**判断标准**：删去某条负向提示后，如果 Agent 不能仅依据正向契约推导出正确行为，说明缺少的是
产物、状态或验证定义；继续追加负面提示只会延缓暴露问题。

## 文档与语体

### P12 句中代码切换

**症状**：中文句子里嵌英文动词或分句：“Stop when 你能用 2-3 句话描述……”、
“prefer 多选题”、“Don't 在同一轮中问一个问题然后用假设自己回答它”。四重代价：
风格不一致稀释指令感；文风泄漏到用户可见输出；翻译腔损耗语义精度；每次编辑都要
重新决定文体。

**修法**：正文自然中文，英文只保留结构锚点——控制标记（STEP/IF/THEN/STOP/PAUSE）、技术术语、章节名、路径、技能名：

```
✅ STOP when 你能用 2-3 句话描述项目的目的、技术栈和结构。
✅ 设计涵盖 architecture、components、data flow、error handling 和 testing。
❌ If 项目复杂或不熟悉，consult the guide for exploration priorities。
```

### P13 多文件规则漂移

**症状**：同一约定在多个文件各写一份，改动只落了一处。真实案例：SKILL.md 删掉了
`.codex/specs/` 路径探测，rubric 里的同一条路径规则还在；SKILL.md 用英文字段标签，
examples 里同一格式用中文标签；两个文件对同一策略用两个名字。

**修法**：约定只在一处定义，其余位置引用该定义（“完整清单见 X”）；改动后全局检索该约定的所有出现位置；跨文件术语对齐纳入审计清单。

### P14 重写的静默语义丢失

**症状**：全文重写（如语体改造）零语义增益，却悄悄丢了行为规则。真实案例：i18n 重写把"P2 打包处理：未勾选的 P2 项写入 Deferred 段落"整段丢了，后续无人察觉。

**修法**：重写前先列出旧版本的行为规则清单，重写后逐条核对；用 `git log -S "<关键短语>"` 追踪短语的增删历史；能给重写单独建 commit 并在 message 里声明"无语义变更"，方便事后审计。

## 产物质量

### P15 无关内容进入下游文档

**症状**：写入文档的内容被后续流程无差别读取，"被拒绝方案的实现细节"因此变成下游的
实现任务。真实案例：Decision Record 里记录了被拒的 Redis Cluster 部署细节，spec-plan
读完生成了"部署 Redis Cluster"的任务——文档里没有任何标记能告诉下游这些是被拒的。

**修法**：为防止无关内容进入下游，制定明确的格式约束（叙述体决策记录：被拒方案只写
“是什么 + 为什么被拒”，实现细节只出现在最终方案的章节），并配可执行的自查手段
（用 Grep 模式扫描决策记录中的库名、端点、配置值，命中则检查上下文）。把风险最高的
反例放进 SKILL.md 主体默认加载，而不是按需的 references。

### P16 凭记忆补写而非重新读取原文

**症状**：长对话末尾写文档时，早期内容已滚出注意力窗口，模型只凭压缩后的记忆补写，
导致措辞变化、细节混淆，甚至添加没讨论过的理由。这类内容看起来合理，比明显编造更难发现。

**修法**：同时防止两类错误：不要编造未讨论过的内容；IF 原始内容已滚出近期对话，THEN
重新读取原文并据此填写，不要凭记忆补写。

### P18 只约束回复语气，没有检查文档正文

**症状**：skill 写了“输出自然、直接”，但这条要求只影响提问和最终回复。生成的项目计划、
设计或评审仍出现逐词翻译、商业黑话、流程隐喻和空泛判断，结构检查与行宽检查都无法发现。

**反例**：评审 finding 只写“当前方案没有形成完整闭环，存在一定风险，建议进一步优化”，
没有说明触发条件、受影响对象、证据或必须修改的内容。

**修法**：让产出型 skill 在写完后重新读取实际文件，并执行可自检的文档语言关卡。关卡
要求具体表达、保护事实和技术字段、禁止语言修改改变需求或状态，完成后重新运行结构、
追踪关系和格式检查。核心规则写在产出型 skill 自身，不依赖另一个 skill 是否安装或触发。
