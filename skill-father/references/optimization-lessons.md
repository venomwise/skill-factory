# Skill 优化失效模式库

从技能的真实迭代中沉淀。每个模式按"症状 → 反例 → 修法"组织，写新技能和审计现有技能时对照使用。反例必须脱离上下文可读：描述事件的形态而不是事件本身，不依赖特定项目名、会话编号或只有当事人才懂的引用。

## 触发与路由

### P1 触发面扩大

**症状**：description 扩大触发范围（如把 bug 修复纳入设计类技能）。description 是技能路由的第一杠杆，改它的收益和风险都被放大，过触发风险随触发面同步增长。

**反例**：description 写"在进行功能开发、bug 修复、优化处理时调用"，正文 "When not to use" 却写"有明确根因的 bug 修复不适用"——两者矛盾，而路由器只看 description。

**修法**：谨慎扩大触发面，确保 description 与正文 "When not to use" 一致。防线只按事实写：实际发生过过触发之后，再基于事实收窄；不要预先添加推测性的防线。

### P2 死路由

**症状**："When not to use" 或路由指引指向目标环境中不存在的技能名。

**反例**：`代码评审 → route to code-review / review`——运行环境里没有这两个技能，agent 照做会悬空。

**修法**：写路由前核实目标技能存在；不确定存在性时改为能力描述："代码级评审不在本技能范围内，应交回相应的评审工具"。

### P3 路由交接不闭环

**症状**：A 技能规定某情形交给 B，B 技能的收尾却没有把该情形送回来。链条在特定路径上断裂。

**反例**：design-review 规定 Reject 裁决要在 refine 后重跑评审；但 design-refine 的收尾只写"设计完备则进入 spec-plan"，Reject 来源的 refine 走完就丢了复审环节。

**修法**：画一遍技能链的完整状态机，每条边从两端各查一次：A 说"交给 B"的情形，B 是否有对应的入口声明和出口路由。

## 对话控制

### P4 技术细节误判为意图确认

**症状**：用户的请求充满技术术语，agent 就跳过澄清直接开干。熟悉技术词汇不等于知道用户想要什么——意图、优先级、取舍偏好只存在于用户头脑中，无法通过检查项目获得。

**修法**：在准入门槛里写死："请求在技术上很详细 does NOT satisfy 意图已确认"；把"本次会话是否至少问过一个澄清性问题"列为硬性检查项。提问一次一个、带上自己的几个理解作为选项（多选优于让用户自由输入）——选项既降低用户回答成本，也能启发用户加深自己的理解。

### P5 自问自答

**症状**：agent 提出问题后不等回答，同一轮里用假设替用户作答继续推进。

**修法**：显式指令"提出问题后停下等待回答，不要用假设代替用户作答"，并说明理由：意图、优先级、验收标准属于只能问、不能猜的信息。

### P6 节奏规则误读为总量上限

**症状**："一次只问一个问题"被执行成"总共只问一个问题"。

**修法**：节奏规则必须自带边界声明："这是节奏控制，不是总量上限；持续提问直到退出条件满足"。

### P7 伪精确阈值

**症状**：给退出条件加模型无法可靠评估的数值阈值，如"问题陈述在最近 2 轮交流中保持稳定"。模型既无法度量"稳定"，又可能被它强制多问一轮，或干脆忽略。

**修法**：退出条件要可自检——改成"你能用用户的原话在 2-3 句话内总结其意图、优先级和约束吗？"这类操作性测试。写不出操作定义的阈值就不要写。

## 流程结构

### P8 prose 关卡无 fallback

**症状**：进入条件写成一段话（"确保已充分理解需求后再继续"），模型无法自检，跳过了也没人知道。

**修法**：关卡写成编号检查清单，每条给"不满足时回哪"的明确动作：

```
1. 是否至少问过一个澄清性问题？If no，回到 STEP 4。
2. 用户能陈述想要什么、为什么、不要什么吗？If no，回到 STEP 4 继续提问。
```

### P9 昂贵动作前缺确认关卡

**症状**：写盘、实施、调用下游技能等昂贵/难撤销动作前没有用户确认，反馈和动作之间出现竞态——agent 抛出方案后立刻开始执行，用户来不及反对。

**修法**：每个昂贵动作前设"呈现 → 等待确认 → 执行"关卡，并写明反馈分流：同意则执行；提出反馈则先判断反馈是否改变意图或方案，再决定就地更新还是回退重做。

### P10 油门指令无刹车配平

**症状**：流程里满是"持续提问直到满足条件""逐项处理每个发现"这类油门，删掉或从未写过"简单场景允许压缩"的刹车。结果琐碎输入被完整流程过度处理。

**修法**：每条油门指令检查是否需要配平项："简单明确的请求允许在少数几轮内完成，不要为凑流程追加环节"。注意油门与刹车的触发条件都要可判断（如引用复杂度分类标准），否则刹车形同虚设。

### P11 记法前缀冲突

**症状**：同一上下文里"D1"既指决策队列序号又指评审维度编号，读者（和模型）必然混淆。序号还有第二个缺陷：队列重排、条目恢复、合并都会使序号漂移，历史引用指向错误条目。

**修法**：一个前缀在一个上下文内只允许一个含义。finding 使用与严重性无关的稳定 ID，
例如 `F-001`；Severity、Origin、轮次和状态分别存储。需要经受队列重排的决策项使用
“标题 + 来源 finding”标识，例如 `错误处理策略（来源: F-003, F-005）`。

### P17 评审-修复循环不收敛

**症状**：评审和修复围绕同一长寿命产物反复迭代，每轮都出现“新”问题，Decision
和 Closure 持续膨胀。常见原因包括：每轮重新执行开放式全量评审；finding 身份与严重性
耦合；refine 把每个 finding 都追加为 Decision；修复内容没有传播到 AC、Data Flow、
Error Handling 和 Testing；评审时 Verdict 与 refine 后 readiness 混在同一视图。

**反例**：某设计在 R3 有 6 条 finding，R4 变为 8 条，其中既有延续和重新打开，
也有 reviewer 前轮漏检。报告只统计“新增”，没有说明问题由 refine 引入、依赖解锁、
基线漏检还是项目事实变化；design 则为每条 finding 追加 Decision 和 Revised 历史。

**修法**：首轮执行 Full Review 并冻结 finding 集合；refine 后默认执行 Closure Review，
只检查旧 finding、changed sections 和固定传播范围。Closure 新 finding 必须声明
`refine-regression`、`dependency-unlocked`、`baseline-miss` 或 `context-change`，并提供因果证据。
finding 使用稳定 `F-###`，Severity 独立。只有持久且非显然的选择进入语义 `DR-*`；
Direct repair 只更新设计章节。用户明确驳回且可能重复出现的 concern 写入带
`Rejected concern` 和 `Revisit when` 的边界 Decision。出口条件是 Current Readiness
为 `ready / Go`，而不是零 finding。

## 文档与语体

### P12 句中代码切换

**症状**：中文句子里嵌英文动词或分句："Stop when 你能用 2-3 句话描述……"、"prefer 多选题"、"Don't 在同一轮中问一个问题然后用假设自己回答它"。四重代价：风格不一致稀释指令感；文风泄漏到用户可见输出（agent 模仿文档腔调说话）；翻译腔损耗语义精度；每次编辑都要重新决定文体。

**修法**：正文自然中文，英文只保留结构锚点——控制标记（STEP/IF/THEN/STOP/PAUSE）、技术术语、章节名、路径、技能名：

```
✅ STOP when 你能用 2-3 句话描述项目的目的、技术栈和结构。
✅ 设计涵盖 architecture、components、data flow、error handling 和 testing。
❌ If 项目复杂或不熟悉，consult the guide for exploration priorities。
```

### P13 多文件规则漂移

**症状**：同一约定在多个文件各写一份，改动只落了一处。真实案例：SKILL.md 删掉了 `.codex/specs/` 路径探测，rubric 里的同一条路径规则还在；SKILL.md 用英文字段标签，examples 里同一格式用中文标签；两个文件对同一策略用两个名字。

**修法**：约定只在一处权威定义，其余位置声明从属（"权威清单见 X"）；改动后全局检索该约定的所有出现位置；跨文件术语对齐纳入审计清单。

### P14 重写的静默语义丢失

**症状**：全文重写（如语体改造）零语义增益，却悄悄丢了行为规则。真实案例：i18n 重写把"P2 打包处理：未勾选的 P2 项写入 Deferred 段落"整段丢了，后续无人察觉。

**修法**：重写前先列出旧版本的行为规则清单，重写后逐条核对；用 `git log -S "<关键短语>"` 追踪短语的增删历史；能给重写单独建 commit 并在 message 里声明"无语义变更"，方便事后审计。

## 产物质量

### P15 长寿命产物的下游污染

**症状**：写进持久文档的内容被下游消费者无差别读取，"被拒绝方案的实现细节"因此变成下游的实现任务。真实案例：Decision Record 里记录了被拒的 Redis Cluster 部署细节，spec-plan 读完生成了"部署 Redis Cluster"的任务——文档里没有任何标记能告诉下游这些是被拒的。

**修法**：为下游污染设计显式格式约束（叙述体决策记录：被拒方案只写"是什么 + 为什么被拒"，实现细节只出现在最终方案的章节），并配可执行的自查手段（用 Grep 模式扫描决策记录中的库名、端点、配置值，命中则检查上下文）。把最危险的污染反例放进 SKILL.md 主体默认加载，而不是按需的 references。

### P16 凭印象重建而非从原文恢复

**症状**：长对话末尾写产物时，早期内容已滚出注意力窗口，模型凭压缩后的印象"重建"——措辞漂移、细节记串、补上没说过的理由。看起来都"像真的"，比凭空编造更难察觉。

**修法**：区分两层防线并都写进指令：防无中生有（"不要编造未讨论过的内容"）+ 防有中生错（"IF 原始内容已滚出近期对话，THEN 回头重读原文并如实恢复，不要凭印象重建"）。
